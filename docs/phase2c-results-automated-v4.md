# Phase 2c 自動測定の結果・版4（条件O・N、Mozc UTの追加辞書、道具の版4）

[評価条件](phase2c-evaluation-protocol.md)の「自動で測る部分」を、mozc.dataにMozc UTの追加辞書を加えた版（[作り方](mozc-ut-dictionary.md)）で測った結果である。同じAPKで始めた[版3の測定](phase2c-results-automated-v3.md)は、道具の版3の明示変換の訂正がアプリの操作と合わなかったため中止した。版3の文書は書き換えず、道具を版4にした測定を別の版として記録する。評価条件の「測定中に見つかった不具合を修正した場合は、修正前の結果を消さず、修正後の結果と版を分けて示す」と、「道具の版を変えた場合は確認してから使い、結果には道具の版を記録する」に従う。

**状態：測定前。** 下の「測定の前に決めた手順」の節は、測定の前にcommitして固定し、測定の後に変えない。

## 測定の前に決めた手順

### 版3の測定の前に決めた手順から引き継ぐもの

[版3の「測定の前に決めた手順」](phase2c-results-automated-v3.md)（commit `171ebbd`で固定）のうち、次を同じにする。

- 評価条件（第2版）、課題文、許容表記、指標、合格基準、除外条件、seed `20261001`、実施順（条件O→条件N、54文を同じ順で1回ずつ）。
- 準備処理（道具の`prepare_condition`で、各条件の前に学習を消す）。
- APK（commit `9aa4ec2`、APK SHA-256 `8eca4c86622a795637f26765cc21b0e23153824f77d0acd646122edd2e381982`、`mozc.data`のSHA-256 `8234a7de58abf8a72f2e89eb6c5ad3f3591045d35bdfef0e69947bf2d2ad0eb8`）。
- 端末の設定の扱い：測定中だけ変換モデルをM（Mozcだけ）にし、設定ファイルとユーザー辞書を退避し、通知の割り込みなしにする。終わったら戻して、開始時の値と照合する。
- 判定の計算（`summarize.py --v2`）と、H1〜H3の基準。

### 中断と除外の扱い

- 計数の途中で道具が止まった課題（中断、または道具の例外による終了）は、評価条件の「記録が欠けた」に当たるため除外し、やり直さない。止まった課題の次の課題から、`--resume-from`で同じ条件の続きを流す（道具が例外で終了した場合も同じ）。
- 計数の前（課題の準備）で止まった場合は、入力を送っていないため除外ではない。同じ課題から続ける。
- 別のアプリの窓が前面に出た課題は除外する。ユーザーが端末を操作している様子があれば、測定を止めて報告する。
- 除外が一つの条件で20%（54課題のうち11課題）を超えたら、その条件を無効にする。
- 止まった課題、除いた課題、続きを流した箇所は、すべて一覧にする。

### 版3と違うもの：道具の版4

| 項目 | 値 |
|---|---|
| 道具 | 版4（commit `dfb7b87`、`run_automated.py` SHA-256 `d6e7a65ca808498e8c631529e58beff4016d6d578440063ded2ea9e18a7b4027`）。測定中に変えない |
| 道具の確認 | [版4の確認](eval-runner-v4-validation.md)の基準・第2版で合格した（commit `5c5d14b`） |

版4で変えたのは、条件Oの訂正（`fix_explicit`）だけである。今のアプリの明示変換（commit `8c4c989`以降）では、候補を選んでも注目文節の表記が変わるだけで、文節は確定せず、注目も動かない。版4は、注目文節の表示が目標の残りの接頭辞なら「→」で次の文節へ移り、そうでなければ候補を選ぶ。過去訂正の条件Oでは、直した後に改行キーを1回押して確定する。

### 計数の読み方（測定の前に固定する）

- **「→」は訂正操作として数える。** 評価条件の操作の分類（カーソル・文節の移動は訂正操作）とIMEの計数（`OperationCounts.kt`）のとおりである。今のアプリの明示変換で後ろの文節を直すには必要な押下なので、そのまま数える。
- **このため、条件Oの訂正操作数と確定操作数は、版3・版2の値と比べられない。** 旧いアプリと道具の版3では、正しい文節を通り過ぎるときに第一候補を選び、確定操作として数えていた。版4では同じ場面で「→」を押し、訂正操作として数える。文節の誤りが同じでも、条件Oの訂正操作数は版の違いだけで増え、確定操作数は減る。第一候補以外を選んだ後に後ろの文節を直す場合も、「→」の分だけ訂正操作数が増える。条件Oの訂正操作数が増えると、H2の訂正操作数の比（N/O）は小さくなる（条件Nに有利な向き）。結果では、この影響を判定と並べて書く。
- **確定だけのために送った改行キーは、確定操作へ読み替える。** 過去訂正の条件Oで最後に送る改行キーは、改行を入れずに確定だけをする。IMEの計数は改行キーを終端操作と数えるが、評価条件では「終端の前に確定だけを目的とした追加の押下は確定操作」である。アプリと計数器は変えずに、道具が課題ごとに残す回数（`commit_enters`）だけ、集計で終端操作から確定操作へ移す（確定操作はキー操作数にも入る）。送った押下とIMEの押下の照合（`input_mismatch`）は、IMEの値のまま行う。
- **訂正の手順の上限**（`MAX_FIX_STEPS` = 30）は変えない。上限に届いた課題（`step-limit`）は、正誤に関わらず一覧にして示し、除外しない。過去訂正の条件Oで最後の候補の選択の直後に上限に届くと、確定の改行キーが送られず、未確定の表示のまま照合される。そのような課題があれば、一覧でその旨を示す。

### 版2・版3との比較

- 版2との違いは参考として並べる。辞書、アプリ、道具の版が違い、それぞれの寄与は分離しない。
- 完了時間は道具の版が違うため、版2と比べない。比較は版4の中の条件Oと条件Nの間だけで行う。
- 条件Oの確定操作数と訂正操作数も、上の理由で版2と比べない。最終正解、無介入正解、条件Nの操作数は参考として並べる。
- 版3の測定は中止しており、値を使わない。
