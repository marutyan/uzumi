# Phase 3a 段階0：入力形式の確認（開発用の30文）

2026-09-24に、[評価条件](phase3a-model-selection-protocol.md)（固定版は`530e75d`）の「段階0」を、Macで開発用の30文（[`phase3a-dev-tasks.tsv`](phase3a-dev-tasks.tsv)）だけを使って行った。試験用の集合（Phase 2cの54文、AJIMEE-Bench）は読んでいない。

## 結論

- 4モデルとも、評価条件の前処理の候補どおりの形式で固定する（下の「固定した入力形式」）。基準を満たさないモデルは無かった。
- **tokenizerの照合（jinen）：一致しなかったプロンプトは0件。** jinen v2 smallで4,075件、xsmallで4,052件の異なるプロンプトすべてで、作者の`tokenizer.json`とllama.cpp内蔵のtokenizerのtoken列が一致した。
- **打ち切り率：4モデルとも0%**（最大出力token 64で、打ち切った要求は0件）。1%を超えなかったため、96での測り直しは行わない。最大出力tokenは64のままとする。
- 出力が空の要求と、壊れたUTF-8の要求は4モデルとも0件。区切り記号（`U+EE00..U+EE0F`）で止まった要求はzenzだけにあった（下表）。
- **文字数の上限（かな30文字、左文脈64文字）は変えない。** 最大のプロンプトtoken数と最大出力tokenの合計は、開発用の集合で最大119（zenz v3.2 smallの55＋64）で、`n_ctx`の512に収まった。上限いっぱいの入力でも、文字の種類から計算した最悪の場合で512に収まる（下記）。
- 開発用の集合に現れない文字のうち、**半角空白を含むプロンプトでは、jinenの2つのtokenizerのtoken列が一致しない**ことを補足の確認で見つけた（下の「補足」）。現在の入力の経路では空白がモデルへ渡らないため、段階0の判定には影響しない。

## 方法

手順は[`tools/phase3a/stage0.py`](../tools/phase3a/stage0.py)、推論は[`tools/phase3a/stage0_probe.cpp`](../tools/phase3a/stage0_probe.cpp)（[ビルド手順](../tools/phase3a/build_stage0_probe.sh)）にある。runtimeはllama.cpp `66afb885`のMac向け静的ライブラリ（[ローカル試作](neural-probe.md)で作ったもの）で、CPUだけ、threads 4、`n_ctx` 512、greedy（logitsの最大）、毎回KV cacheを消す。モデルは[ローカル試作](neural-probe.md#モデルhugging-facerevision固定)の4ファイル（revisionとSHA-256固定）である。

### モデルへの要求の作り方

段階2の逐次入力で作られるプロンプトを、辞書（Mozc）なしで次のように再現した。

1. 各課題の`読み`を1打鍵ずつ入れたときの各時点の読みを作る。濁点・半濁点・小書きの文字は、端末の「小゛゜」キーと同じく基の文字を経由する（例：「が」は「か」の時点を経る）。30文で650時点。
2. **基本の要求**：各時点の読み全体を一つの部分範囲とし、端末の`NeuralRangeConverter`と同じ規則でかなの連なりだけをモデルへ渡す。左文脈は同じ部分範囲で先に出した表記（数字・英字はそのまま、かなの連なりはモデルの出力）とする。かなの連なりが30文字を超える場合は30文字ごとに区切る（端末ではMozcの文節境界で区切るため、これは最長の場合に当たる）。
3. **保護範囲がある要求**：保護範囲の表記も左文脈になるため、各時点の読みを任意の位置で「前が保護範囲、後ろが部分範囲」に分け、前の部分をモデルで変換した表記を左文脈にした要求も作った。どの位置が実際に保護範囲になるかは端末のコアが決めるため、ここではすべての位置を含めた（実際より多い）。
4. 同じプロンプトは1件と数える（端末のcacheに当たる）。

打ち切り率などの率は基本の要求（各モデル459件の異なるプロンプト）で、tokenizerの照合とtoken数の最大は基本と保護範囲がある要求の全体で求めた。

### tokenizerの照合

jinenでは、各プロンプトについて、llama.cpp内蔵のtokenizer（`llama_tokenize`、`add_special=false`、`parse_special=true`）のtoken列と、作者の`tokenizer.json`によるtoken列（karukanと同じ`encode(text, add_special_tokens=false)`）を比べた。

HuggingFace tokenizersのライブラリは作業環境に無く、新しい導入を避けるため、`stage0.py`の`HfBpeTokenizer`に、このファイルの設定に限った同じ手順（added tokenの分離、NFKC、数字の切り離し、結合の優先順位によるBPE、byte fallback）を実装して使った。llama.cppの内蔵tokenizerは、語彙のscoreで結合を選ぶ別の手順（SentencePiece系）である。**公式のライブラリでの照合は行っていない**（下の「限界」）。

zenzは作者のtokenizerの別ファイルが無いため、評価条件どおり内蔵のtokenizerを基準とし、照合はしていない。

### 区切り記号での停止

zenzの区切り記号での停止は、変換した表記の後に`U+EE00`（次の読みの始まり）か`U+EE08`を出したものだった。ZXの基本の要求28件の内訳は`U+EE00`が20件、`U+EE08`が8件。記号より前の表記は、多くが読み全体を変換したもの（例：「まど」→「窓」）だった。ZSの基本の要求の1件は`U+EE01`で止まり、記号の前が読みに無い繰り返しを含んでいた（「かぞくにもこうひ」→「家族にも好評で、家族にも好評でした。」）。評価条件どおり、区切り記号での停止は正常な終わりとして記号より前を使い、読みとの対応は検査1〜4で確かめる。この出力はかなの並びが読みと合わないため検査3で捨てられる。

### token数の上限

開発用の集合では、かなの連なりは最大25文字、左文脈は最大41文字で、30文字・64文字の上限には届かなかった。上限いっぱいの入力でも、最悪の場合（左文脈がすべて語彙に無い4 byteの文字でbyte tokenへ分かれる）で、zenzは区切り記号9 token＋かな30＋左文脈256＝295、jinenは区切り記号3＋かな90（すべて3 byteへ分かれた場合）＋左文脈256＝349で、出力の64を足しても512に収まる。

### 参考：Macでの推論時間

基本の要求の1件あたりの時間（プロンプトの処理と生成の合計、ミリ秒）の中央値／p95は、ZS 12.0／25.4、ZX 3.6／7.3、JS 9.2／19.8、JX 3.0／6.1だった。Mac（Apple M3 Pro）での値であり、端末の性能やモデル間の優劣の根拠にしない。

## 固定した入力形式

評価条件の前処理の候補をそのまま固定する。端末の実装（JNIの橋渡しの前のKotlin側）とこの手順で同じ規則を使う。

| 項目 | zenz v3.2（ZS、ZX） | jinen v2（JS、JX） |
| --- | --- | --- |
| 各欄の除去 | 左文脈と読みから`U+EE00..U+EE0F`と制御文字（`U+0000..U+001F`、`U+007F`）を除く | 同じ |
| 読み | ひらがな（`ぁ`〜`ゖ`、`ゝゞ`）をカタカナへ写す | 同じ |
| 形 | 左文脈があるときだけ`U+EE02`＋左文脈、続けて`U+EE00`＋読み＋`U+EE01` | 左文脈が空でも`U+EE02`＋左文脈、続けて`U+EE00`＋読み＋`U+EE01` |
| 正規化 | 半角空白を全角空白へ（改行は上の除去で消える） | プロンプト全体をNFKC |
| tokenize | 内蔵のtokenizer、`add_special=false`、`parse_special=false` | 内蔵のtokenizer、`add_special=false`、`parse_special=true` |
| 停止 | EOG、または出力に`U+EE00..U+EE0F`が現れた時点（記号より前を使う）。最大出力token 64に達したら打ち切りとして捨てる | 同じ |
| 文字数の上限 | かなの連なり30文字、左文脈64文字（後ろの64文字を使う） | 同じ |

## 補足：開発用の集合に無い文字

判定には使わない補足として、左文脈に入り得る架空の断片14個（[`tools/phase3a/stage0_tokenizer_extra.py`](../tools/phase3a/stage0_tokenizer_extra.py)）で、jinenの2つのtokenizerを比べた。空白を含む3個（半角空白、全角空白、英単語の間の空白）だけが一致しなかった。連続した数字、全角英数、丸数字、`〇`、記号、絵文字、半角カナ、単独の濁点は一致した。

一致しない理由は、llama.cppのSentencePiece系のtokenizerが空白を必ず`U+2581`へ置き換える（この語彙に`U+2581`は無く、3つのbyte tokenになる）のに対し、`tokenizer.json`は空白をそのまま語彙の空白tokenにするためである。例：左文脈「午後 3時」は、`tokenizer.json`では`… 12590, 260, 279 …`、内蔵では`… 12590, 230, 154, 133, 279 …`になる（NFKCで全角空白も半角になるため、全角空白でも同じ）。

現在の入力の経路では、空白キーはcompositionを確定してから空白を入れる（`EditorSession.insertSpace`）ため、空白がcompositionの読みにも左文脈にも入らない。左文脈は同じcompositionの中の表記だけなので（[設計](neural-direct-conversion-design.md#左文脈)）、この不一致は段階2の要求には現れない。確定済みの文字列を左文脈に使う場合や、空白を含む記号をcompositionへ入れられるようにする場合は、その前に対応を決める（要確認）。

## 限界

- `tokenizer.json`によるtoken列は、公式のHuggingFace tokenizersではなく、このファイルの設定に限った再実装で求めた。結合の選び方が異なる2つの実装が4,000件余りで一致し、空白という既知の違いでだけ一致しなかったことは再実装が正しい根拠になるが、公式のライブラリとの照合ではない。公式のライブラリで確かめるにはその導入が要る（未実施）。
- 要求は辞書なしで再現したもので、端末では、Mozcの文節境界での区切り、辞書の結果を左文脈にする場合、実際に保護範囲になる位置が異なる。保護範囲の位置はすべてを含めたため、実際の要求は照合した集合より少ない。端末で作られた実際のプロンプトの照合は段階2の前には行えない。
- 打ち切り率などは開発用の30文の値で、試験用の集合での値は分からない。
