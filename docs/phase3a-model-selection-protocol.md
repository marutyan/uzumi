# Phase 3a モデル選定の評価条件（案）

**状態：案（2026-09-24）。ユーザーの承認前であり、この条件による比較実験はまだ実行しない。** 承認した時点のcommit IDを「固定版」とし、以後の結果にはその固定版を記録する。

根拠は[開発計画](../plans/development-plan.md)のPhase 3a、[変換エンジンの調査](research/conversion-engines.md)の「単一ニューラルモデルを決める実験」、[評価計画](research/ux-and-evaluation.md)、[ニューラル直接変換の設計案](neural-direct-conversion-design.md)、[ローカル試作](neural-probe.md)、[Phase 2cの評価条件](phase2c-evaluation-protocol.md)である。

## 目的と仮説

目的は、「ニューラルで直接変換し、辞書で補う方式」で製品に載せるモデルを一つ選ぶことである。製品にはモデルの切り替えを設けず、選んだ一つだけを配布する。

| 番号 | 仮説 | 反証となる結果 |
| --- | --- | --- |
| H1 | 候補のモデルを使うと、Mozcだけのライブ変換より、無介入正解文率が上がる | 差の95%区間の下限が0以下 |
| H2 | 候補のモデルを使っても、訂正操作と表示の揺れは悪化しない | 訂正操作数の下限またはflickerが合格基準を超えて増える |
| H3 | 候補のモデルを使っても、過去の正しい表記、stable・chosen、数字・英字を書き換えない | 1件でも発生する |
| H4 | 候補のモデルは、端末で速度・メモリ・電池の目標に収まる | どれか一つでも目標を超える |

H3は件数の多少ではなく発生の有無で判断する。

- 量子化は4モデルともQ5_K_Mにそろえる。量子化による品質低下を切り分ける追加の比較（jinen v2 smallのQ8_0とF16）は、Q5_K_Mの結果を見た後に別途承認を得て行う。zenz v3.2はQ5_K_M以外の公開を確認していないため、同じ切り分けはできない。
- ZS・ZX・JS・JXは、同じ`NeuralRangeConverter`（同じcommit）と同じMozc（commit、`mozc.data`）を使い、モデルとモデルごとのプロンプト形式だけを変える。プロンプト形式は[ローカル試作](neural-probe.md#プロンプト形式の違い)の表に固定する。
- 推論の設定は全モデルで同じにする：threads 4、`n_ctx` 512、greedy、最大token 64、時間超過300 ms（すべて仮。承認時に確定）。
- ユーザー辞書は空、学習履歴は各条件の開始前に消す。

## 課題集合

調整用と試験用を分ける。試験用は、下の「固定と変更の規則」で固定した後に各条件で一度だけ流す。

| 集合 | 中身 | 用途 | 利用条件 |
| --- | --- | --- | --- |
| 開発用 | 新しく作る30文（Phase 2cと同じ9分類から各3〜4文、架空の内容）と練習6文 | プロンプト形式の確認、時間超過・長い入力の区切りなどの値の調整、手順の確認 | 未作成。本書の承認後に作り、試験の前に文と許容表記の承認を得る。試験用と同じ文や言い換えを入れない |
| 試験用A | [`phase2c-tasks.tsv`](phase2c-tasks.tsv)の評価用54文 | 逐次入力の再生（主指標） | 承認済みの課題と許容表記をそのまま使い、追加・削除しない |
| 試験用B | [AJIMEE-Bench](https://github.com/azooKey/AJIMEE-Bench/tree/401666cd56d1a570c2021798b64b6da4396bfd45) `JWTD_v2/v1`の200問（commit `401666cd56d1a570c2021798b64b6da4396bfd45`） | 一回の変換の正解率（補助指標） | 下記 |

AJIMEE-Benchの扱い：

- データはCC BY-SA 3.0（元の日本語Wikipedia入力誤りデータセットv2に準拠）、評価コード`utils.py`と`test_utils.py`はCC0 1.0とREADMEに書かれている。データはGit追跡外の`.local-build/phase3a/`へ取得し、リポジトリには入れない。リポジトリへは問題の`index`ごとの正誤と集計値だけを残す。モデルの出力文字列を問題ごとに公開するかは、派生物としての扱いを確認してから決める（要確認）。
- 入力は完成したカタカナの読みで、左文脈付き100問と文脈なし100問からなる。逐次入力やライブ変換の揺れは測れないため、合否ではなく補助指標にする。
- jinenの作者はこのベンチマークで自作モデルの値を公表している。モデルの開発でこのベンチマークを見て選んだ可能性を否定できないため、この集合だけの差でモデルを選ばない。元データがWikipedia由来のため、各モデルの学習データに同じ文が含まれるかは不明である。

Phase 2cの課題文は、Phase 2cの常用試験でも使う。Phase 3aの調整に使わないことで、両方の試験の意味を保つ。

## 測り方

### 段階1：Macでの一回の変換（モデルだけ）

- 試験用Bの200問と、試験用Aの54文の`読み`全体を、各モデルで一回ずつ変換する。Mozcは使わない（Mac向けのMozcをビルドしていないため）。
- 読みの形式：試験用Bはデータのカタカナのまま、試験用Aはひらがなをカタカナへ写す。左文脈は試験用Bの`context_text`だけを使う。
- 正解：試験用Bは`expected_output`のいずれかとの完全一致（exact@1）。NFKCをかけた一致は参考として併記する。試験用Aは許容表記のいずれかとの完全一致。
- 同じMac、同じ条件（CPUだけ、threads 4）で、推論時間の分布も参考として記録する。端末の性能の根拠にはしない。

### 段階2：端末での逐次入力の再生（主指標）

- Phase 2cの自動測定の手順（`adb`によるキー入力、評価用計数、`uiautomator`による最終文の取得）を使い、試験用Aの54文を条件ごとに同じ順で流す。人の操作は含めない。
- ニューラルの条件では、評価用計数に次を足す（本文は残さず件数と時間だけ）：モデルへの要求数、不採用（読みとの対応の失敗）の数、時間超過の数、Mozcへ切り替えた数、推論時間、入力の受理から結果の適用までの時間、数字・英字のsegmentの表記が読みと異なった数。これらの計数の実装とJVMテストは、試験を始める前に済ませる（本書の範囲外）。
- 条件の順番は、固定seed（仮に`20261015`）で並べ替え、seedと順番を記録する。各条件の間に5分以上空け、`dumpsys thermalservice`の温度状態が`NONE`に戻ってから始める。
- 速度とメモリは、同じ54文を3回流して集める。品質の指標は1回目だけを使う。

### 指標

| 指標 | 定義 | 段階 |
| --- | --- | --- |
| exact@1 | 一回の変換の出力が正解のいずれかと完全に一致した割合 | 1 |
| 無介入正解文率 | 読みの入力と本来の終端操作だけで、最終文が許容表記に一致した文の割合（Phase 2cと同じ定義） | 2 |
| 訂正操作数の下限 | 最終文が許容表記と一致しない場合に、候補の照合で機械的に直すのに必要な操作数（Phase 2cと同じ手順） | 2 |
| 最終正解率 | 機械的な訂正の後に許容表記へ到達できた文の割合。候補に正解が無い文を分けて数える | 2 |
| flicker | 変換結果の到着で、既に変換済みの表示が変わった回数を読み100文字あたりで表す（Phase 2cの評価用計数と同じ） | 2 |
| 誤書換え | `stable_overwrites`、`chosen_overwrites`、数字・英字の改変の数 | 2 |
| 不採用率 | モデルの出力のうち、読みとの対応の検査で捨てた割合 | 2 |
| 時間超過率 | 推論が時間超過でMozcへ切り替わった割合 | 2 |
| 推論時間 | `:neural`が要求を受けてから結果を返すまで。p50、p90、p99 | 2 |
| 適用までの時間 | 最新の入力の受理から、結果をコアへ適用するまで。p50、p90、p99 | 2 |
| 常駐メモリ | `:neural`とIMEのプロセスのPSS。モデル読み込み前、読み込み後の待機、連続入力中の最大。`dumpsys meminfo`で1秒ごと | 2 |
| cold start | `:neural`が無い状態からbindし、最初の推論結果が返るまで。10回の中央値と最大 | 2 |
| メモリ制限による終了 | `am memory-limiter status`と`ApplicationExitInfo`（`REASON_OTHER`かつ`MemoryLimiter:AnonSwap`）の記録 | 2 |
| 電池 | 54文の再生を10分間くり返したときの端末全体の推定消費（`dumpsys batterystats`、充電を切った状態）。Mとの比 | 2 |

## 実機の条件

- 端末はPixel 10 Pro（Android 17）。`ro.build.fingerprint`、画面の明るさ（固定値）、リフレッシュレート、省電力の設定、充電の状態、温度状態、`am memory-limiter status`を記録する。
- 充電は`dumpsys battery unplug`で切った扱いにし、試験後に`dumpsys battery reset`で戻す。USB給電の影響が残るため、電池の値は条件間の比としてだけ使う。
- 別の担当が同じ端末で測定中の場合は、その測定が終わってから行う。
- Uzumiはdebuggableでないprofileableなbuild（release相当の設定）で測ることを基本とし、評価用計数を含めるため難しい場合はdebug buildとその理由を記録する。

## 合格基準（案、すべて仮の値）

以下の数値は仮であり、根拠となる測定はまだ無い。承認時に値を確定し、測定後に変えない。

| 対象 | 基準 |
| --- | --- |
| 安全（必須） | 誤書換え（stable、chosen、数字・英字の改変）、crash、ANR、メモリ制限による終了が0件 |
| 速度 | 推論時間のp95 ≤ 100 ms、適用までの時間のp95 ≤ 300 ms、時間超過率 ≤ 1% |
| メモリ | `:neural`の連続入力中の最大PSSが、small ≤ 150 MB、xsmall ≤ 80 MB |
| cold start | 中央値 ≤ 2 s。IMEの入力はモデルの準備を待たずにできる |
| 電池 | Mとの比 ≤ 1.2 |
| 品質（H1） | 無介入正解文率のMとの差（文単位の対応のある差）の、bootstrap 95%区間の下限 > 0 |
| 品質（H2） | 訂正操作数の下限の中央値 ≤ Mの値、flicker ≤ Mの1.5倍 |

- bootstrapは文単位で10,000回、seed固定（仮に`20261015`）。検定の有意差は合否の条件にしない。
- 分類ごとの結果を表と図で示す。全体が合格でも、特定の分類（数値、URL、英語混在など）で安全の不具合があればその候補は不合格とする。

## 選び方

1. 安全、速度、メモリ、cold start、電池の基準をすべて満たす候補だけを残す。
2. 残った候補のうち、H1・H2を満たすものを残す。
3. その中で無介入正解文率が最も高い候補を選ぶ。最も高い候補との差の95%区間が0を含む候補が複数あれば、その中で`:neural`のPSSが小さい方、次に電池の比が小さい方を選ぶ。
4. 試験用Bのexact@1は、3でも決まらない場合の参考にだけ使う。
5. 残る候補が無ければ、Mozcだけのライブ変換を続ける。Q8_0などの量子化、モデルの追加、方式の見直しのどれに進むかは、結果を示して改めて判断する。

## 固定と変更の規則

- 承認後は、比較条件、モデルのrevisionとSHA-256、runtimeのcommit、プロンプト形式、推論の設定、課題集合、指標の定義、合格基準、選び方、seedを変えない。
- 試験の開始前に、次のcommitとSHA-256を記録して固定する：Uzumiのcommit、APKのSHA-256、`NeuralRangeConverter`を含むcommit、Mozcのcommitと`getDataVersion()`、llama.cppのcommit、`.so`のSHA-256、モデルのSHA-256、評価用計数の版。
- 変える必要が見つかった場合は、本書を新しい版として理由とともに記録し、それ以前の結果は旧版の基準で判定したまま残す。
- 試験の途中で不具合を直した場合は、直す前の結果を消さず、直した後に**全条件を**同じ版で流し直す。一部の条件だけを流し直して比べない。

## test集合を調整に使わない規則

- 次の調整は開発用の集合だけで行う：プロンプト形式の細部、時間超過、推論のthread数と`n_ctx`、長い入力を区切る長さ、読みとの対応の検査の規則、候補の並び、数字を含む範囲の扱い、評価手順。
- 試験用A・Bの結果を見た後に、上の項目を変えて同じ試験用の集合で比べ直さない。変える場合は新しい版として開発用の集合で決め直し、試験用は新しい版で全条件を流し直す。その場合も、旧版の結果と見比べて有利な版を選ばない。
- 試験用の文を、プロンプトの例、辞書、学習、テストのfixtureへ入れない。
- 開発用の集合で見つかった誤りの修正は許す。修正の内容と、どの開発用の文で見つかったかを記録する。

## データの保存

- 生の記録（モデルの出力、評価用計数、`dumpsys`の出力、AJIMEE-Benchのデータ）はGit追跡外の`.local-build/phase3a/<実施日>/`に置く。
- リポジトリへは、課題IDごとの正誤と数値、集計表、図、図の元データ、生成コードを`docs/`へ残す。
- 日常入力の本文は使わない。記録に本文、候補、clipboardを残さない（試験用の文とその出力を除く）。

## 承認を求める事項

1. 比較条件：Mozcだけを基準線にし、4モデルをQ5_K_Mだけで比べること。量子化の切り分け（jinen v2 smallのQ8_0・F16）は後で別に判断すること。
2. runtimeを4モデルとも`66afb885`（azooKey forkの`b9637-compat`）にそろえること。
3. 課題集合：開発用30文を新しく作ること、Phase 2cの54文を試験用Aに使うこと、AJIMEE-Benchを補助指標の試験用Bに使い、データをリポジトリへ入れないこと。
4. 端末での段階2を主指標とし、段階1は補助にすること。
5. 推論の設定（threads 4、`n_ctx` 512、時間超過300 ms）と合格基準の仮の値。
6. 選び方（差が決まらなければメモリ、次に電池の小さい方）。
7. 追加する評価用計数の項目と、その実装を試験の前に行うこと。
