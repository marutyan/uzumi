## 目的と仮説

目的は、「ニューラルで直接変換し、辞書で補う方式」で製品に載せるモデルを一つ選ぶことである。製品にはモデルの切り替えを設けず、選んだ一つだけを配布する。

| 番号 | 仮説 | 反証となる結果 |
| --- | --- | --- |
| H1 | 候補のモデルを使うと、Mozcだけのライブ変換より、無介入正解文率が上がる | 補正した区間の下限が0以下 |
| H2 | 候補のモデルを使っても、訂正操作、表示の揺れ、正しい表示が誤った表示へ変わる回数は、事前に定めた許容幅を超えて悪化しない | 訂正操作数の平均差、flickerの比、正→誤の遷移の平均差のどれかで、補正した区間の上限が許容幅を超える |
| H3 | 候補のモデルを使っても、stable・chosen、入力した数字・英字を書き換えず、かなの読みから辞書の候補に無い数字・英字を作って表示しない | 適用後の違反が1件でもある |
| H4 | 候補のモデルは、端末で速度・メモリ・電池の目標に収まる | どれか一つでも目標を超える |

H3は件数の多少ではなく発生の有無で判断する。provisionalの表示は設計上、後の入力で変わってよいため、「正しい暫定表示が誤った表示へ変わる」ことはH3に入れず、H2の指標「正→誤の遷移」として基準線Mとの差で判定する（下記）。入力した数字・英字はモデルへ渡さない設計のため、その改変はニューラルの条件では原則0になる。ニューラルに固有の失敗（かなの読みから誤った数字を作る。例：「じゅうじ」→「11時」「0時」、「にせんにじゅうろくねん」→「1999年」「26年」）は、下の「H3の数え方」で検査とは独立に数える。

## 手順の順序

1. 本書と開発用の30文を承認する。
2. 段階0（入力形式の確認）と、開発用の集合での設定の調整を行う。
3. 調整を終えた設定（プロンプト形式、最大出力token、時間超過、長い入力の区切り、検査の規則、評価手順）と、下の「固定と変更の規則」の各commit・SHA-256を記録して**最終設定として固定する**。固定した内容は本書の追記として残す。
4. 試験用A・Bを、固定した最終設定で各条件に流す（段階1・段階2）。
5. 選び方に従って候補を決め、配布可否の関門を通す。

## 段階0：入力形式の確認（開発用の集合だけ）

モデルごとのプロンプト形式と停止条件を、試験の前に開発用の集合で確かめる。結果を記録してから形式を固定する。

- **tokenizerの一致（jinen）**：作者の`tokenizer.json`（jinen v2 small・xsmallの同じrevisionにあるもの、2,047,498 bytes。取得は承認事項）とllama.cppの内蔵tokenizerで、開発用30文の全プロンプト（段階2の逐次入力で実際に作られる各プロンプト。左文脈を含む）のtoken列を比べる。1件でも一致しなければ形式を固定せず、不一致の例を示して対応（内蔵tokenizerの修正、`tokenizer.json`を使う実装、該当文字の前処理）を決め直す。zenzは作者のtokenizerの別ファイルが無いため、内蔵tokenizerを基準にする。
- **前処理**：次の形式を固定の候補とし、開発用の集合で出力が空・途中で終わる・区切り記号を含む割合を記録する。
  - zenz：読みをカタカナへ写す。左文脈があるときだけ`U+EE02`を付ける。半角空白を全角へ、改行を除く。
  - jinen：読みをカタカナへ写す。左文脈が空でも`U+EE02`を付ける。プロンプト全体をNFKC正規化する。
- **停止条件**：EOGか、出力中の`U+EE00..U+EE0F`で止める。最大出力tokenに達した場合（打ち切り）は検査1・2で捨てる。モデルごとに、開発用の集合での打ち切り率（打ち切った要求数÷要求数）を記録する。打ち切り率が1%を超えるモデルは、最大出力tokenを96に上げて一度だけ測り直し、結果を記録する。それでも1%を超えるモデルは、打ち切り率を報告した上で試験へ進め、段階2の時間超過率・不採用率で評価する。
- **文字数の上限**：tokenの数え方がモデルで違う（zenzはほぼ1文字1 token、`U+EE00`などは3 token。jinenは語の単位で、区切り記号は1 token）ため、上限はtoken数ではなく文字数で全モデル共通にする。モデルへ渡すかなの連なりは最大30文字、左文脈は最大64文字とする。開発用の集合で、各モデルの最大のプロンプトtoken数＋最大出力tokenが`n_ctx`（512）に収まることを確かめて記録する。収まらないモデルがあれば、全モデル共通の文字数の上限を下げる（モデルごとに変えない）。

## 測り方

### 段階1：Macでの一回の変換（モデルだけ、補助）

- 試験用Bの200問と、試験用Aの54文の`読み`全体を、各モデルで一回ずつ変換する。Mozcは使わない（Mac向けのMozcをビルドしていないため）。検査4は辞書が要るため、ここでは適用しない。
- 読みの形式：試験用Bはデータのカタカナのまま、試験用Aはひらがなをカタカナへ写す。左文脈は試験用Bの`context_text`だけを使う。
- 正解：試験用Bは`expected_output`のいずれかとの完全一致（exact@1）。NFKCをかけた一致は参考として併記する。試験用Aは許容表記のいずれかとの完全一致。
- 数字の照合：下の「最終文の数字の並び」の規則を、出力と正解の組にも当てはめ、件数を記録する。
- 推論時間の分布も参考として記録する。端末の性能の根拠にはしない。

### 段階2：端末での逐次入力の再生（主指標）

- Phase 2cの自動測定の手順（`adb`によるキー入力、評価用計数、`uiautomator`による最終文の取得）で、試験用Aの54文を流す。人の操作は含めない。
- **同一のAPKと計数**：Mを含む全条件を、同じAPK（同じcommit、同じSHA-256）、同じ評価用計数の版で測る。条件の切り替えはdebug buildの設定（`adb`から送る評価用の設定）で、ニューラルの無効化（M）とモデルのファイルの指定（ZS・ZX・JS・JX）だけを変える。Mでもニューラル側の計数の列は出し、0であることを確かめる。
- **同一の入力間隔**：キーの間隔は全条件で150 ms（Phase 2cの値）に固定する。
- **回と順番**：品質・速度・メモリは5回に分けて測る。各回で5条件を一つずつ流し、条件の順番は5×5のラテン方格で入れ替える（各条件が各位置に一度ずつ当たる）。方格の行の割り当てはseed `20261015`で決め、記録する。各条件の間に5分以上空け、`dumpsys thermalservice`の温度状態が`NONE`に戻ってから始める。
- 品質の指標は、文ごとに5回の値の平均をとり、その文を一単位として集計する（greedyのため回ごとの差は主に時間超過と古い結果の破棄から生じる。回ごとの値も併記する）。
- **ニューラル側の計数**（本文は残さず件数と時間だけ）：モデルへの要求数、かなの連なりへの分割の数（部分範囲あたり）、長い入力を区切った数、cache hitの数、中断の数、時間超過の数、検査で捨てた数（検査1〜4の別）、Mozcへ切り替えた数、読みのまま表示した数、推論時間、入力の受理から結果の適用までの時間、下の「H3の数え方」の各件数。これらの計数の実装とJVMテストは、試験を始める前に済ませる（本書の範囲外）。結果の表には、品質の値と並べて分割とfallbackの回数を必ず示す。

### 正→誤の遷移の数え方（H2）

最終文だけを照合すると、正しい暫定表示が誤った表示へ変わり、最終文で元へ戻った場合を見逃す。そこで、Phase 2cの評価用計数が`display_changes`と`flicker`を数える時点（変換結果の到着によってEditorの表示が変わった各時点）ごとに、次を判定する。

- 各時点の表示について、許容表記のいずれかと先頭から一致する最長の長さ（書記素の数）を「正しい接頭部」とする。
- 変換結果の到着による表示の変更で、正しい接頭部が短くなり、失われた範囲が変更前に変換済みの表示だった場合を「正→誤の遷移」1回と数える。一回の結果の適用は、何か所変わっても1回とする。ユーザーの操作による表示の変更は数えない。
- 失われた範囲がstableまたはchosenだった場合は、H3の`stable_overwrites`・`chosen_overwrites`にも当たる。
- 評価モードは課題IDから許容表記を引いて端末内で判定し、判定の結果（件数）だけを残す。表示の文字列は残さない（Phase 2cの方針と同じ）。
- 限界：最初の誤りより後ろの範囲の正誤は判定しない。

この計数の実装とJVMテストは、試験を始める前に済ませる（本書の範囲外）。

### H3の数え方（検査とは独立に数える）

検査4が正しく働いていることを前提にせず、次の3つを分けて数える。

**実装時の条件：** 生成件数と適用後の違反件数を数える関数は、`NeuralRangeConverter`の検査4（`hasDictionaryBackedDigitsAndLetters`）を呼ばず、評価用計数の側に別に実装する。照合に使うMozcの文節と候補も、変換器を通さず評価用計数がMozcから直接取り出す。JVMテストでは、検査4を無効にした変換器の出力に対して、この計数が違反を数えることを確かめる。

| 計数 | 数える時点 | 定義 |
| --- | --- | --- |
| 生成件数 | 検査の前 | モデルの出力に含まれる数字・英字の連なりのうち、同じ読みの範囲をちょうど覆うMozcの文節の候補の連結と完全一致しないものの数。検査の実装とは別の関数で数える |
| 拒否件数 | 検査の結果 | 検査4がその出力を捨てた数 |
| 適用後の違反件数 | コアへ適用した後 | 表示へ適用した結果のsegmentのうち、生成件数の定義に当たる数字・英字を含むものの数。検査が正しければ0 |

さらに、**最終文の数字の並び**を許容表記と独立に照合する。最終文と各許容表記から、数字の連なり（全角は半角へ直す）を順に取り出した列を作り、最終文の列がどの許容表記の列とも一致しない文を「数字の違反」として数える。許容表記に漢数字の表記（例：「三百円」）と算用数字の表記（「300円」）の両方がある場合は、どちらかの列と一致すればよい。この照合は最終文が許容表記と完全一致しない文にも行う。

H3の判定は、適用後の違反件数と数字の違反が全条件で0件であることとする。生成件数と拒否件数は、候補ごとの傾向として報告する（安全基準の判定には使わない）。ただし、生成件数に当たる出力のうち検査1〜4のどれでも捨てられなかったものが1件でもあれば、適用後の違反件数が0でも、検査か計数の不具合として試験を止める。

### 速度の母集団

- **推論時間**：5回の再生で、モデルへ実際に送った要求（cache hitを除く）すべて。時間超過した要求は、時間超過の値（300 ms）で打ち切った値として含める（p95が300 msに張り付けば、それ自体が不合格を示す）。新しい入力で中断した要求は含めず、件数と中断までの時間を別に示す。cache hitの数と割合を併記する。
- **適用までの時間**：5回の再生で、コアへ結果を返したすべての変換要求（cache hit、Mozcへの切り替え、読みのままの表示を含む）について、その要求を作った入力の受理から結果の適用までの時間。コアが古い結果として捨てた要求は含めず、件数を別に示す。
- p95などは条件ごとに全要求を一つにまとめて計算する。回ごとのp95も併記し、回によって合否が分かれる場合はその旨を記録する。

### 電池の測り方

- 試験用Aの54文の再生を10分間くり返し、充電を切った状態（`dumpsys battery unplug`）の`dumpsys batterystats`から端末全体の推定消費を得る。試験後に`dumpsys battery reset`で戻す。
- 各条件を3回測る。3回を3つの別の日または時間帯に分け、各回で5条件の順番をラテン方格の別の行で入れ替える。「別の日または時間帯」は、前の回と日付が違うか、前の回の開始から4時間以上空いていることとする（2026-09-24に承認）。
- 同じ回の中のMとの比（候補÷M）をとり、3回の比の平均で判定する。3回の比の最小値と最大値が基準（1.2）をまたぐ場合は判定不能とし、2回を追加して5回の平均で判定する。追加後もまたぐ場合は、安全側として不合格とする。

## 実機の条件

- 端末はPixel 10 Pro（Android 17）。`ro.build.fingerprint`、画面の明るさ（固定値）、リフレッシュレート、省電力の設定、充電の状態、温度状態、`am memory-limiter status`を記録する。
- USB給電の影響が残るため、電池の値は条件間の比としてだけ使う。
- 別の担当が同じ端末で測定中の場合は、その測定が終わってから行う。
- Uzumiはdebuggableでないprofileableなbuild（release相当の設定）で測ることを基本とし、評価用計数と条件の切り替えを含めるため難しい場合はdebug buildとその理由を記録する。どちらの場合も全条件で同じAPKを使う。

## 合格基準（仮の値として承認済み）

以下の数値は仮の値として承認された。根拠となる測定はまだ無い。測定後に変えない。

| 対象 | 基準 |
| --- | --- |
| 安全（必須） | 誤書換え（stable、chosen、入力した数字・英字の改変、H3の適用後の違反件数、数字の違反）、crash、ANR、メモリ制限による終了が0件 |
| 速度 | 推論時間のp95 ≤ 100 ms、適用までの時間のp95 ≤ 300 ms、時間超過率 ≤ 1% |
| メモリ | 連続入力中の最大PSSが、`:neural`でsmall ≤ 150 MB・xsmall ≤ 80 MB、IMEと`:neural`の合計でMの条件のIMEの最大PSS＋150 MB（small）・＋80 MB（xsmall）以下 |
| cold start | 中央値 ≤ 2 s。IMEの入力はモデルの準備を待たずにできる |
| 電池 | 上の「電池の測り方」による比 ≤ 1.2 |
| 品質（H1） | 無介入正解文率の、候補とMの文ごとの差の平均について、補正した区間の下限 > 0 |
| 品質（H2） | 次の三つをすべて満たす。訂正操作数の下限の、候補とMの文ごとの差の平均について、補正した区間の上限 ≤ +0.1（1文あたり）。flickerの比（候補÷M）の、補正した区間の上限 ≤ 1.5（Mが0の場合は下記）。正→誤の遷移の、候補とMの文ごとの差の平均について、補正した区間の上限 ≤ +0.05（1文あたり） |

### 多重比較と区間の求め方

- 4候補をそれぞれMと比べるため、H1・H2の区間は同時に4回判定する。Bonferroniの補正で、各比較の区間を両側98.75%（1−0.05/4）とする。
- 区間は文を単位とする対応のあるbootstrap（10,000回、seed `20261015`）で求め、パーセンタイル法で端点をとる。flickerの比は、再標本ごとに「候補のflicker回数の合計÷読みの文字数の合計」を「Mの同じ値」で割って計算する。
- **flickerでMが0の場合：** 標本全体でMのflickerが0なら、候補も0のときは合格、候補が1回以上なら不合格とする（比は計算しない）。bootstrapの再標本でMの合計が0になった場合は、候補の合計も0ならその再標本の比を1、候補が正なら+∞として区間の計算に含める。上限が+∞になれば不合格とする。
- **合否は、補正した区間と事前に定めた基準だけで判定する。** p値による検定は使わない。H1は「補正した区間の下限 > 0」、H2は「補正した区間の上限 ≤ 許容幅」で判定する。区間の幅と、文ごとの差の分布の図も示す。
- **検出力が低いこと：** 試験用Aは54文と少ないため、実際に差があっても区間が0や許容幅をまたぎ、「差が決まらない」結果になりやすい。H2は区間の上限で判定するため、区間が広いと悪化していなくても不合格になりやすい。この結果を前提に、文の数を後から増やして同じ集合で判定し直すことはしない（新しい集合が必要なら下の規則に従う）。
- **差が決まらない結果を「同等」と報告しない。** 区間が0をまたぐ場合は「差が決まらない（区間は…）」と書き、「同等」「差が無い」とは書かない。同等を主張する場合は、同等とみなす幅と検定の方法を事前に決めた別の試験が要る（本書では行わない）。
- 分類ごとの結果を表と図で示す。全体が合格でも、特定の分類（数値、URL、英語混在など）で安全の不具合があればその候補は不合格とする。

## 選び方

1. 安全、速度、メモリ、cold start、電池の基準をすべて満たす候補だけを残す。
2. 残った候補のうち、H1・H2を満たすものを残す。
3. 候補間の比較は、試験の前に**4候補のすべての組（4×3÷2＝6組）**を比較の対象と決めておく。各組について無介入正解文率の文ごとの差の平均の区間を、Bonferroniの補正で両側99.17%（1−0.05/6）として求める。組の数は、1・2で残った候補の数によらず6組のまま補正する。その中で平均が最も高い候補を「最良」とし、最良との組の区間が0を含む候補を「最良と差が決まらない候補」とする。最良を選んだ後に比較の数を減らして補正し直すことはしない。
4. 最良と差が決まらない候補の中から、次の順で一つに決める：連続入力中の`:neural`の最大PSSが小さい方、電池の比が小さい方、モデルのファイルが小さい方。
5. 試験用Bのexact@1は、4でも決まらない場合（値が同じ）の参考にだけ使う。
6. 残る候補が無ければ、Mozcだけのライブ変換を続ける。Q8_0などの量子化、モデルの追加、方式の見直しのどれに進むかは、結果を示して改めて判断する。
7. 選んだ候補を、次の「配布可否の関門」に通す。

## test集合を調整に使わない規則

- 最終設定に含まれる項目の調整は、開発用の集合だけで行う。
- 試験用の文を、プロンプトの例、辞書、学習、テストのfixtureへ入れない。
- **試験用A・Bの結果を見た後の改版は「探索」とする。** 探索の結果は探索と明記して報告し、採用の判断には使わない。探索で有望な版が見つかった場合、採用の判断には、試験用A・B・開発用のどれとも重ならない**新しい未使用の集合**を用意し、同じ手順（作成、承認、最終設定の固定、一度だけの試験）で判定する。新しい集合は作成の時点で承認を得る。
