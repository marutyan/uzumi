# ライブ変換のIME接続と検証

確認日：2026-09-23。[ライブ変換の状態設計](live-conversion-design.md)の状態機械`dev.uzumi.ime.live.LiveConversionCore`を、IMEの編集セッションとMozc（公式`google/mozc` commit `13c98988247aa711d99db9e348ec2a597d14b5cd`、[明示変換の記録](mozc-conversion-validation.md)と同じ生成物）へ接続した。ライブ変換ONでは、打つたびに変換結果が表示され、句点・改行・Editor actionで確定操作なしに確定する。過去segmentの訂正、取り消し、ユーザー辞書の登録語の候補、設定画面のON/OFFと第三者ライセンス表示を加えた。

## 構成

| 役割 | 実装 | 要点 |
| --- | --- | --- |
| Editorへの書込み | `EditorSession.applyLiveUpdate` | コアの`EditorCommand`（`SetComposition`、`Commit`、`PerformEditorAction`）をInputConnectionへ送る唯一の経路。`SetComposition`は明示変換と共通の`writeComposition`で送り、selection通知の照合に使う期待値を同じ規則で記録する。書込みに失敗したら接続を閉じ、同じ本文を再送しない。 |
| 入力欄ごとの切替 | `InputFieldPolicy.usesLiveConversion`、`UzumiSettings` | 入力開始ごとに設定を読み、ONかつ通常の文字欄ならライブ変換、それ以外（OFF、password、`TYPE_NULL`、数字・電話・日時、URL、メール）は従来の明示変換にする。学習禁止欄はライブ変換を使い、要求へ学習禁止を付ける。 |
| 範囲分割 | `SegmentedLiveConverter` | 要求の対象範囲を、保護範囲（stable/chosen、Undoで戻した範囲、カーソルを含む範囲）と対象範囲内の入力カーソルで区切り、自由な部分範囲ごとに変換する。各範囲の境界が必ずsegment境界になるため、コアの照合で結果が捨てられない。ASCIIだけの範囲はMozcへ送らず入力のまま表示する。 |
| Mozcの変換 | `MozcConversionEngine.convertSegments` | 部分範囲の読みを`AS_IS`で積み（`Input.request_suggestion=false`で入力途中の予測を求めない）、`SPACE`で変換する。preeditの各文節の`key`と`value`を読み、focusを`RIGHT`で右へ動かしながら、強調された文節の`all_candidate_words`から候補を取る。`key`が文節の読みの接頭辞でない候補（予測）と`num_segments_in_candidate`が2以上の候補（複数文節）は除く（2026-09-24に直した。末尾の「文節の候補と区切りの伸縮」を参照）。確定しないため学習は起きない。文節の読みの連結が範囲と一致しない場合は、範囲全体を一segmentにする。 |
| 学習 | `ConversionWorker.learnCommitted`、`MozcConversionEngine.learnSegments` | 確定したsegment列を、句読点・未変換・ASCIIのsegmentで区切った単位ごとに学習させる。単位の読みを変換し、文節の幅をShift+右・左で伸縮して区切りを合わせ、表記が違う文節は`SELECT_CANDIDATE`で選んでから`SUBMIT`する。合わせられなければ`REVERT`して確定せず、segmentごとに学習し直す。自動変換、候補の選択、Undoだけでは学習させない。学習禁止欄では送らない。 |
| 直列worker | `ConversionWorker` | 明示変換と同じ単一threadだけがJNIを呼ぶ。ライブ変換も未処理の要求は最新の一件だけを変換する。学習と`endSession`は呼び出し時点で終了判定し、同じ世代のsession破棄より先にキューへ積むため、Send直後に欄が閉じても確定した内容を学習できる。 |
| ユーザー辞書 | `UserDictionaryCandidates` | 各segmentの読みに完全一致する登録語を登録順に候補の先頭へ置き、最初の語を表示する（自動表示）。Mozc候補との重複は除く。部分範囲全体の読みに一致する語があれば、範囲を一segmentにまとめてその語を表示する。明示変換では、読み全体に一致する語があればその最初の語を読み全体の一文節として表示し、読み全体と先頭文節に一致する語を候補の先頭へ置く。明示変換では、登録語を選ぶか表示のまま確定してもMozcへ通知しない。ライブ変換では、登録語の表記がMozcの候補にも無ければその単位は学習させない。候補にある場合（例：「はし」→「箸」を登録）は、他の確定と同じく学習させる。辞書はworkerの初期化時に開き、UIスレッドで初めて読まない。 |
| 候補バー | `UzumiInputMethodService.refreshLiveCandidates` | 対象segmentの候補を常時表示し、現在の表記を太字にする。左右に「◀」「▶」（前後のsegmentへ。読点は飛ばす）、「末尾」（入力位置へ戻る）、「取消」（直前の操作を取り消す）を置く。訂正中のsegmentはEditor上で背景色を付ける。変換済み表示の内部をEditorでタップすると、そのsegmentを対象にしてカーソルを入力位置へ戻す。変換キーは対象segmentの次の候補を選ぶ。 |
| 設定・表示 | `MainActivity`、`LicenseActivity` | ライブ変換のON/OFF（既定ON）をSharedPreferencesへ保存する。第三者ライセンスはAPKのassets`licenses/mozc-NOTICE.txt`を原文のまま表示する。 |

Mozcが使えない間（読み込み中・辞書なし）は要求を送らず、部分範囲ごとに読みとカタカナを候補にする。機密欄では明示変換と同じく要求を作らない。

明示変換（OFF）の表示中に削除すると、従来どおり読み末尾の書記素を消して表示を読みへ戻し、自動では再変換しない（「良い」→削除→「よ」）。独立レビューで、自動の再変換の結果が次の文字の入力で確定される不具合（「良い」→削除→「夜」→「る」で「夜」が確定）が見つかったため、この動作に戻した。ライブ変換では、変換済みsegmentの末尾の削除はそのsegmentだけを読みへ戻して再変換する（コアの既存規則）。

selection通知の照合に残す過去のcompositionの数（`EditorSession.MAX_STALE_COMPOSITIONS`）は8から32へ増やした。ライブ変換では一打鍵で読みの表示と変換結果の表示の2回（カーソルが末尾以外なら位置の指定を加えて最大4回）書き込むため、8では2〜4打鍵分の遅れしか照合できない。照合できない遅延通知は外部の変更とみなしてcompositionを確定・破棄するので、速い連続入力で誤って確定しないようにした。

## 未確認・既知の制限

- 訂正中のsegmentへ背景色を付けると、試用欄ではcompositionの下線が表示されなかった。確定・入力の動作は変わらない。
- 文脈を含む読み（「こうえんにいく」）での学習の効き方は、末尾の「文脈が違う読みでの学習」で原因を確かめ、IME側の学習で補った。
- 設定の切替は次の入力開始から反映する。同じ欄でキーボードを閉じて開いただけでは反映されない。
- Compose TextField、WebView、回転、プロセス再作成、長文での変換時間とメモリ使用量、TalkBackでの候補バーの操作。
- 学習禁止欄（`IME_FLAG_NO_PERSONALIZED_LEARNING`）での実機確認（JVMテストだけ）。
- 数字・英字・記号が混ざる読みのライブ変換。ASCIIだけの範囲はMozcへ送らないが、混在する範囲はMozcの正規化によって範囲全体が一segmentになる場合がある。
- ライブ変換で登録語を表示したまま確定すると、その単位のMozcへの学習は表記を合わせられず取り消される（登録語はMozcの辞書に無いため）。登録語以外の隣のsegmentは、segmentごとの学習し直しで学習される。

## 文脈が違う読みでの学習（2026-09-23）

### 不具合と原因

ライブ変換で「こうえんにいく」の「公園に」を「校園に」へ直し、「校園に行くよ」と確定しても、次に「こうえんにいく」と打つと「公園に」のままだった。Mozcの`segment.db`は更新されていた。

原因はMozcの文節履歴の仕様であり、Uzumiが送る学習の命令列の誤りではない（確定）。根拠は`src/rewriter/user_segment_history_rewriter.cc`の次の条件である。

- 確定時の書き込み（`Finish`→`RememberFirstCandidate`）は、`FIXED_VALUE`の文節ごとに、前後の文節の表記を含む特徴（`LR`、`LL`、`RR`、`L`、`R`）、変換全体が一文節の場合の`Single`、文脈を含まない`Current`を保存する。`Current`は、文節の幅を変えた変換（`segments.resized()`）、`CONTEXT_SENSITIVE`の候補、既定の候補と置き換えられない候補（`Replaceable`：機能語の表記と品詞グループが同じ）では保存しない。
- 次の変換での参照（`Rewrite`→`GetScore`）も同じ条件で、`Current`は置き換えられる候補にだけ使う。それ以外の候補は、前後の文節の表記が学習時と一致する特徴でしか先頭へ上がらない。`L`系の特徴は確定済みの履歴文節も前の文節として数える。

同じcommitのMozcをhost向けにビルドした`session_handler_main`（`bazel build //session:session_handler_main --config oss_macos`）で、既定の`Request`のまま次を再生した。入力はローマ字で、Uzumiの`AS_IS`のかな入力とは経路が違うが、変換と学習は同じ処理を通る。

| 学習した確定 | 次の変換 | 先頭 |
| --- | --- | --- |
| 「こうえんにいくよ」→「校園に行くよ」 | 「こうえんにいく」 | 公園に |
| 同上、2文節目を縮めて「校園に行く よ」 | 「こうえんにいく」 | 公園に |
| 「こうえんに」→「校園に」（一文節） | 「こうえんに」／「こうえんにいく」／「こうえんにはいる」 | 校園に／公園に／公園に |
| 「こうえんにいく」→「校園に行く」 | 同じ読み／「こうえんにいくよ」 | 校園に／公園に |
| 「こうえんに」→「公演に」（一文節） | 「こうえんにいく」／「こうえんにはいる」 | 公演に／公演に |
| 「きしゃが」→「汽車が」（一文節） | 「きしゃがのる」 | 汽車が |

「公演に」「汽車が」は既定の候補と置き換えられるため、別の文脈でも先頭になる。「校園に」は置き換えられないと判定され、学習時と同じ文節の並びでしか先頭にならない。「かんじ→幹事」が効いたのは、一文節の変換で`Single`と`Current`が一致したためである。Mozcの判定を変えずにUzumiの命令列だけで一般に効かせる方法は無いため、Mozcへの学習の送り方は変えず、IME側に学習を持つことにした。

## 句の学習（2026-09-23）

IME側の学習キャッシュへ、segmentの語に加えて、同じ確定単位の中の句を覚えるようにした。スミレ（`KazumaProject/JapaneseKeyboard`、MIT、commit `1db923c7`）の`learning/session/ConversionLearningSession.kt`が確定時に「選び直した文節」「先頭からの累積句」「読み全体」をまとめて記録する仕組みを参考にし、コードは移さずに書いた。

### 記録

| 項目 | 規則 |
| --- | --- |
| 確定単位 | `liveLearningUnits`が作る単位（句読点・未変換・ASCIIだけのsegmentで区切った、続いた変換済みsegment）。Mozcへ学習させる単位と同じ。 |
| 句 | 2segment以上の単位で、先頭からの累積句（1〜2番目、1〜3番目…）。最後の句が単位の読み全体になる。読みと表記はそれぞれsegmentの連結。 |
| 除外 | 句の読みと表記にも`LearningRules.isLearnable`（ひらがなだけ、ASCIIだけ、読みと同じ、50文字超、タブ・改行）を当てはめる。学習OFF、機密欄、学習禁止欄では、segmentと同じく記録しない（学習禁止欄は`learnCommitted`自体が呼ばれない）。 |
| 登録語を含む句 | 登録語を表示したsegmentの手前で句を打ち切る（例：「今日｜は｜渦見｜です」は「今日は」だけ）。登録語を含む句を覚えると、辞書から消した後も学習から登録語が表示され続けるためで、segmentの登録語を記録しない既存の規則と同じ理由である。 |
| ひらがなだけのsegmentを含む句 | 句の一部としてなら記録する（「今日｜は」→「今日は」）。助詞・送り仮名・かなで書いた語は句の表記の一部であり、除くとほとんどの句が作れないためである。句の表記全体がひらがなだけなら記録しない。 |
| 新しい句を作る条件 | 句の中に、ユーザーが候補を選んだsegment（`SegmentState.CHOSEN`、`LearnedSegment.chosen`）があるときだけ新しく作る。選ばずに確定した句はエンジンの結果の再現で、覚えても表示は変わらず上限を埋めるだけだからである。既に覚えている句は、選ばずに確定しても時刻と回数を更新する（使い続ける句が古くなって捨てられないようにする）。スミレも、選び直した文節を含む句だけを記録している。 |
| 語と句の区別 | `LearnedWord.isPhrase`。区別は作ったときのまま保ち、同じ読みと表記を後でsegmentとして確定しても変えない（上限の数え方にだけ使うため）。 |

### 参照

| 場面 | 規則 |
| --- | --- |
| ライブ変換・範囲全体 | `SegmentedLiveConverter`が区切った部分範囲の読み全体に一致する学習語（句を含む）があれば、既存の規則どおり範囲を一segmentにして、その表記を表示する。 |
| ライブ変換・範囲の先頭 | 範囲全体に登録語も学習語も無く、範囲の先頭からの読み（範囲より短い）に一致する句があれば、最も長い句を選ぶ。句の読みと残りの読みを別々に変換し、句の範囲は句の表記の一segment（候補は「句 → エンジンの連結 → 読み」）にする。句の終わりが新しいsegment境界になる。 |
| 保護範囲とカーソル | 句は部分範囲の中だけで探す。部分範囲は保護範囲（stable/chosen、Undoで戻した範囲、カーソルを含む範囲）と対象範囲内の入力カーソルで区切られているため、それらの境界を越える句は使われない。 |
| 明示変換 | 既存の`LearnedCandidates.mergeExplicit`のまま、読み全体に一致する句をエンジンの第一候補の前へ置き、表示は変えない。読みが入力の読みで始まる句は、前方一致の予測として候補の最後へ入る。 |
| 学習禁止欄 | ライブ変換・明示変換とも句を参照しない。 |

句の範囲を一segmentにするのは、範囲全体に一致する登録語・学習語を一segmentにする既存の規則に合わせたためである。句の内部の区切りを戻すには保存形式へ区切り位置を足す必要があり、今回は行わない。句の一部だけを直したい場合は、候補にあるエンジンの連結を選ぶか、読みへ戻して打ち直す。

### 上限と減衰

- 全体の上限は10,000語のまま、そのうち句を3,000語（30%）までにする。句が上限を超えたら、segmentの語がより古くても、scoreが最も低い句から捨てる。全体が上限を超えたら、従来どおり最も低い語を捨てる。一回の確定で句は最大「segment数−1」個増え、読みが長い句は同じ読みを打つ機会が少ないため、上限を分けないと短い読みで繰り返し効くsegmentの語を句が押し出すためである。30%は、選んだsegmentを含む句だけを作る条件と合わせて語を十分に残せると見込んだ仮値で、実際の分布では確かめていない。
- 減衰は従来のscore（`最後に使った時刻 + ln(回数) × 1日`）で扱い、期限による削除は加えない。scoreは最後に使った時刻が基準のため、使われない句は新しい句より先に捨てられる。期限で消すと、季節ごとに使う語のように間隔が空いても正しい語まで消えるためである。上限に達するまでは古い句も残るが、句は読みの完全一致（範囲の先頭では句の読みまでの一致）でしか使われない。

### 保存形式

`learning.tsv`の句の行だけ、5列目に`phrase`を書く。4列の行はsegmentの語として読むため、句を導入する前のファイルはそのまま読める。先頭行の識別子（`uzumi-learning-v1`）は変えていない。句を導入する前のアプリで新しいファイルを読むと、5列の行（句）だけが読み捨てられる。

- 実機では確かめていない。

## 文節の候補と区切りの伸縮（2026-09-24）

Phase 2cの自動測定（branch `validation/phase2c-automated`の`docs/phase2c-results-automated.md`）で、ライブ変換の最終正解率が66%となり、明示変換の94%より低かった。誤った19件はすべて、目標の表記が候補バーにも候補一覧にも無かった。原因は二つあり、両方を直した。

### 候補が少なかった原因

確定（Mozcの固定checkout `13c98988…`のソースと、偽のMozcによるJVMテストで確認。実機では未確認）。ライブ変換は、候補の`CandidateWord.key`が文節の読みと違うものを予測として除いていた。しかしMozcは、候補の自立語部分の読み（`content_key`）が文節の読みと違うときに`key`へ入れる（`engine/engine_output.cc`の`FillCandidateWord`）。自立語部分の読みは、`nbest_generator.cc`の`MakeCandidate`で助詞などの機能語より前の読みを連結したものである。そのため「講演に」（`key`「こうえん」）や「降っています」のように、機能語を含む普通の候補がほとんど除かれていた。Phase 2cで残っていた「項園に」「校園に」やかな・カナの候補は、`content_key`が文節の読みと同じだった候補と考えられる（推測。候補ごとの`content_key`は記録していない）。明示変換はこの除外をしていないため、同じ読みでも候補が多かった。

`candidates`の上限（`max_conversion_candidates_size`は既定200）と、focusを動かして取る範囲は原因ではなかった。どちらも明示変換と同じである。

### 変更

| 対象 | 変更 |
| --- | --- |
| 自動変換の候補 | `key`が文節の読みの接頭辞なら残す（`content_key`は常に候補の読みの先頭部分になるため）。接頭辞でない`key`と、`num_segments_in_candidate`が2以上の候補は、従来どおり除く。自動変換の命令数は変えていない。 |
| 注目した文節の候補の取り直し | ←→で注目した文節と、候補一覧（∨）を開いた文節だけ、前後の文節の読みを文脈に付けて変換し直す（`MozcConversionEngine.convertSegment`）。文脈と対象の文節はShift+左・右で一文節ずつに合わせ、明示変換と同じく各候補を一時的に選んで文節の区切りが変わらない候補だけを集める。確定はせず、学習もさせない。要求（`CandidateRequest`）はsessionEpoch・revision・辞書の世代・segmentのid・読みの範囲を持ち、結果はすべてが一致する場合だけ候補へ加える。表示とrevisionは変えないため、表示済みの候補のタップは有効なままである。ユーザー辞書の登録語と学習語は自動変換と同じ順で合成する。一度取り直した文節には、同じ読み範囲・同じ表記である限り再び要求しない。 |
| 文節の区切りの伸縮（ライブ変換） | 変換中は←→を押して離すと文節の移動、長押しで対象の文節の終わりを一書記素ずつ縮める・伸ばす（300 msごとに繰り返す）。伸縮した範囲は変換要求の`fixedRanges`に入り、変換器は保護範囲と同じくその両端で区切って一segmentとして変換する（Mozcでは`convertSegment`で幅を合わせる）。結果を適用するとその文節はchosenになり、以後の自動更新から守られる。縮めて外れた書記素は未変換に戻り、後ろの自由な範囲と一緒に変換し直される。伸ばして取り込んだ後ろの文節は、残りを未変換へ戻す。入力カーソルを内部に含むことになる伸縮と、読点をまたぐ伸縮はしない。伸縮はUndo可能な一操作である。区切りを守らない結果は`CROSSES_FIXED`、伸縮より前の要求への結果は`REVISION_MISMATCH`で捨てる。 |
| 文節の区切りの伸縮（明示変換） | 変換結果の表示中に←→を長押しすると、候補を出している先頭文節を一書記素ずつ縮める・伸ばす。変換要求に先頭文節の書記素数（`headLength`）を付け、Mozcで先頭文節の幅を合わせてから候補を集める。明示変換は先頭文節ごとに確定して残りを変換し直すため、先頭文節だけを対象にした。 |
| TalkBack | ←→キーの操作メニューに「文節を縮める」「文節を伸ばす」を加えた（変換中だけ）。一回の実行で一書記素動く。 |
| Phase 2cの計数 | 伸縮（`KeyboardAction.ResizeSegment`）は訂正操作として一回ずつ数える（`OperationClassifier`）。変換中の←→は、押した瞬間ではなく離したときに一回だけ移動する。候補の取り直しの結果は変換結果ではないため、捨てた古い結果（`stale_results_discarded`）には数えない。伸縮した文節が結果でchosenになると、`to_chosen`に数えられる。 |

### 未確認・既知の制限

- 実機では確かめていない。Phase 2cの失敗例（C01「こうえんに」の「講演に」、N01の「降っています」、D01の「に｜会いましょう」）が直るかは、実機でMozcを動かして確かめる必要がある。偽のMozcのテストは、Mozcのソースから読んだ`key`の付け方を再現したものであり、実際の辞書の候補の並びは確かめていない。
- 取り直しは、前後の文節を一文節ずつに合わせてから変換するため、自動変換より遅い。注目したときと一覧を開いたときだけ行うが、長い文節や候補の多い読みでの待ち時間は測っていない。
- 伸縮は文節の終わりだけを動かす（Mozcと同じ）。「似合いましょう」を「に｜会いましょう」にするには、前の文節を伸ばすか、「にあいましょう」を「に」まで縮める。
- ライブ変換の伸縮で外れた書記素は、後ろの文節が自由なら一緒に変換し直されるため、後ろの文節の表記も変わることがある。後ろがstable・chosenなら外れた書記素だけで変換する。
- 明示変換の伸縮は先頭文節だけである。先頭文節以外の文節へは移れない（既存の明示変換の文節の扱い）。
