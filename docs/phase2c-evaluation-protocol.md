# Phase 2c 常用試験の評価条件

**状態：承認済み（2026-09-23）。** 承認した時点のcommit IDを「固定版」とし、以後の結果にはその固定版を必ず記録する。

根拠は[開発計画](../plans/development-plan.md)のPhase 2c・3a、[評価計画](research/ux-and-evaluation.md)の指標案と測定方法、[ライブ変換の状態設計](live-conversion-design.md)の状態と境界である。課題文は[`phase2c-tasks.tsv`](phase2c-tasks.tsv)に置く。

## 目的と仮説

目的は、Uzumiのライブ変換を日常入力に使えるかを、同じ文課題で現用IMEと比べて判断することである。Phase 2cの完了条件「ライブON/OFF、既存IMEと操作数・時間・誤書換えを比較」と、次へ進めない条件「安全性の未解決不具合、訂正コストの悪化」を判定できる形にする。

| 番号 | 仮説 | 反証となる結果 |
|---|---|---|
| H1 | ライブONは、ライブOFFより文あたりの確定操作数を減らす | 確定操作数が減らない、または無介入正解文率がOFFと同程度以下 |
| H2 | ライブONは、確定操作を減らしても訂正操作と完了時間を悪化させない | 訂正操作数または完了時間がOFFより合格基準を超えて増える |
| H3 | ライブONは、ユーザーが変更していない過去の正しい表記を書き換えない | 過去の正解の破壊、chosenの侵害、古い結果による上書きが1件でもある |
| H4 | ライブONの入力は、現用IME（Simeji）と比べて常用できる範囲の操作数と時間に収まる | キー操作数または完了時間がSimejiより合格基準を超えて多い |

H3は安全性の条件であり、件数の多少ではなく発生の有無で判断する。

## 比較条件

| 条件 | 内容 |
|---|---|
| S：現用IME | ユーザーが現在使っているSimeji。設定は変えず、試験時の設定を記録する |
| O：Uzumi ライブOFF | 明示変換。読みを入れ、変換キーまたは候補選択で確定する |
| N：Uzumi ライブON | ライブ変換。正しい表示のまま句点や改行で確定できる |

- 端末はPixel 10 Pro、縦向き、同じ持ち方（ユーザーが普段使う持ち方を最初に一つ決めて記録し、全条件で同じにする）。
- 配列は3条件とも12キーのフリック入力、英字はQWERTY、数字は各IMEの数字配列とする。Simejiのトグル入力・フリック感度などの設定は変えず、値を記録する。
- 入力先は、端末外へ本文を送らない同じ試験用の複数行EditTextとする（Uzumiの試用画面を第一候補とする。同期機能を持つメモアプリ、ブラウザの検索欄は使わない）。
- Uzumiの2条件は同じAPK・同じ辞書で、ライブ設定だけを変える。ユーザー辞書は空にし、Mozcの学習履歴は各条件の開始前に消す。課題文の許容表記をIME、辞書、学習へ入れない。
- Simejiの学習履歴は消さない。現用の状態との比較であり、学習の有無が条件間で異なることを結果の限界として記録する。

前提（試験開始前に満たすこと）：ライブ変換がIMEへ配線され、ライブON/OFFを切り替えられること。Uzumiの評価用計数（後述）が本文を保存しない形で実装され、JVMテストで確認されていること。これらは本書の範囲外であり、未実装なら試験を始めない。

## 課題文

課題文は`phase2c-tasks.tsv`に置く。列は`id`、`分類`、`リスト`、`読み`、`許容表記`、`指示`である。許容表記は`|`で区切り、いずれかと完全に一致すれば正解とする。指示の`-`は指示なしを表す。

| 分類 | 件数 | 狙い |
|---|---:|---|
| 通常文 | 6 | 一般的な短文 |
| 同音異義語 | 6 | 文脈で表記が決まる語 |
| 名前 | 6 | 架空の人名・地名。表示した表記だけを正解とする |
| 数値 | 6 | 数字・単位・記号。全角と半角は課題ごとに許容表記で列挙する |
| URL | 6 | 自動変換を避けるべき英数字列。`example.com`など予約済みのドメインだけを使う |
| 長文 | 6 | 読点を含む35〜45文字の文 |
| 過去訂正 | 6 | 句点まで入力した後、前の語を指示した表記へ直す |
| 句点なし | 6 | 句点を入れず改行キーで終える短文 |
| 英語混在 | 6 | 英単語をQWERTYで入れる文 |
| 練習 | 6 | 評価に使わない |

- 評価用は9分類×6文＝54文。各分類の6文をリストA・B・Cへ2文ずつ割り当てる（各リスト18文）。
- 課題文はすべて架空であり、個人情報、実在の個人を指す名前、実在のサービスのURLを含まない。
- 許容表記、正規化（全角・半角、句読点、送り仮名）は試験前にこのファイルで確定し、測定後に追加・削除しない。表記揺れを許すかは「日常入力で本人が受け入れる表記か」で決める。
- 過去訂正の課題は、自然な第一候補になりにくい表記を目標にしている。変換が最初から目標どおりになった場合は、訂正なしで正解としてよい（訂正の回数を強制しない）。

## 指標

句点、改行キーでの終了、送信などの本来の終端操作は、どの操作数にも含めない。ただし、終端の前に確定だけを目的とした追加の押下が必要なら、それは確定操作に数える。

| 指標 | 定義 | 測り方 |
|---|---|---|
| 無介入正解文率 | 読みの入力と本来の終端操作だけで（確定操作・訂正操作が0回で）、最終文が許容表記に一致した文の割合 | 操作の分類と最終文から判定する |
| キー操作数 | 課題の開始から終了までに画面へ指が触れた回数。フリックは1回、長押しの連続削除も1回と数える | 下の「測り方」参照 |
| 確定操作数 | 誤りのない表示を確定するためだけの操作。変換キー、正しい第一候補の選択、確定のための追加押下 | 操作の分類 |
| 訂正操作数 | 誤った表示や入力を直す操作。削除、segmentの選択、第一候補以外の候補選択、Undo、再入力 | 操作の分類 |
| 完了時間 | 課題の最初のタッチから、最後の終端操作のタッチまで（ミリ秒） | タッチの時刻 |
| 最終正解 | 最終文が許容表記に一致したか。上の指標と併記し、誤文のまま操作を減らした結果を良い結果と扱わない | 最終文の照合 |
| 誤書換え | ユーザーが変更していない範囲が、後の入力で正しい表記から誤った表記へ変わった回数。chosenの侵害、古い結果による上書きを別に数える | Uzumiの評価用計数 |
| flicker | 同じ読み範囲の自動の表示変更回数を、読み100文字あたりで表す。初回の表示と手動の変更は除く | Uzumiの評価用計数 |

誤書換えとflickerはライブ変換を持つ条件Nの指標である。条件Oは参考として記録し、条件Sは測れないため「対象外」と書く（0とは書かない）。

## 測り方

端末で自動化する部分と、ユーザー本人の操作が必要な部分を分ける。両者の数値は混ぜて集計しない。

### 自動で測る部分（Uzumiの条件O・N）

目的は、人の打ち間違いを除いた変換と状態の挙動を、同じ入力で再現可能に比べることである。

- 読みの入力：課題の`読み`を、Uzumiのキーの位置（`adb shell uiautomator dump`で取得したキーの範囲）とフリック方向の列へ変換し、`adb shell input tap`と`adb shell input swipe`で送る。キーの間隔は一定値（仮に150 ms）とし、記録する。
- 長押しを含む操作は使わない。`input tap`は端末の処理の遅れで押下が長くなり、削除キーの連続削除に入ることがあるため、削除キーは押下時間を固定したDOWNとUPで送る（連続削除の保留を加える案は採用していない）。
- 最終文：終端操作の後に`uiautomator dump`で試験欄の文字列を取り、許容表記と照合する。
- 訂正：最終文が許容表記と一致しない場合は、目標表記と候補一覧を照合して必要な候補を選ぶ手順を機械的に行う。このときの訂正操作数は「必要な操作数の下限」であり、人の訂正コストとは別の値として報告する。目標表記は照合にだけ使い、IMEへは渡さない。
- 評価用計数：Uzumiのdebug buildに、評価モードを明示的に有効にした間だけ、操作の種別ごとの回数、表示の自動変更の回数、誤書換えの判定に必要なsegmentの状態変化、時刻を記録する仕組みを設ける。評価モードは`adb`からの設定で入れ、試験の終了時に切る。記録には課題IDを付け、入力本文・候補の文字列は残さない。誤書換えの判定に表記が必要な場合は、課題文と照合した結果（正誤）だけを残す。
  - 実装済みの範囲：課題ごとの操作数（キー操作数、確定操作数、訂正操作数、終端操作数）。表示の自動変更の回数、segmentの状態変化、時刻は未実装であり、flickerと誤書換えを測る前に別作業で足す。
  - 操作の分類（計数の版1、`app/src/main/java/dev/uzumi/ime/evaluation/OperationCounts.kt`）：句点の入力とEnterは終端操作。明示変換の変換キーと第一候補の選択は確定操作。削除、行頭までの削除、カーソル・文節の移動、第一候補以外の候補選択、元に戻す、「末尾」、カナへの切り替え、ライブ変換中の変換キー（次の候補）は訂正操作。キー操作数は終端操作を除くすべての押下で、面の切替、Shift、候補一覧の開閉も含む。長押しの連続削除は、計数器では消えた回数ずつ数える。これは上の指標の定義（1回と数える）と異なるため、自動測定では長押しを使わず、本人が操作する条件では`getevent`で押下を数えて定義どおり1回とする。取り消した削除ドラッグのように、IMEへ操作が届かない押下は数えない。
  - 課題ごとの手順（debug APKだけで使える）：
    1. 試験欄を空にする：`adb shell am start -n dev.uzumi.ime/.compat.Phase2cTaskActivity --es task <課題ID>`。開くたびに欄（`dev.uzumi.ime:id/phase2c_task_field`）を空にし、課題IDを表示する。この操作は数えない。
    2. 計数を始める：`adb shell am broadcast -n dev.uzumi.ime/.compat.EvaluationCounterReceiver -a dev.uzumi.ime.debug.EVAL_START --es task <課題ID>`。課題IDは英数字・`_`・`-`の16文字以内に限る。
    3. 読みを入力し、終端操作まで行う。
    4. 計数を終える：`adb shell am broadcast -n dev.uzumi.ime/.compat.EvaluationCounterReceiver -a dev.uzumi.ime.debug.EVAL_FINISH`。出力の`data`に1行（`counter_version`、`task_id`、`keys`、`commits`、`corrections`、`terminators`のTSV）が返り、端末内の`no_backup/phase2c-counts.tsv`へも追記される。
    5. 最終文を`uiautomator dump`で試験欄から取る。
  - 取り出しと消去：`-a dev.uzumi.ime.debug.EVAL_DUMP`で全行を、`-a dev.uzumi.ime.debug.EVAL_CLEAR`で記録の消去と計数の停止を行う（どちらも上と同じ`-n`で送る）。`adb shell run-as dev.uzumi.ime cat no_backup/phase2c-counts.tsv`でも読める。取り出した結果は`.local-build/phase2c/<実施日>/`へ置く。受信口はDUMP権限を持つ`adb shell`からだけ送れ、releaseビルドには入らない。
- 実施：条件Oと条件Nで54文を同じ順に1回ずつ流す。条件ごとに学習履歴を消してから始める。

### ユーザー本人が操作する部分（条件S・O・N）

目的は、実際の指による操作数、完了時間、主観を、現用IMEと同じ課題で比べることである。

- 課題文は端末外（PCの画面）に1文ずつ表示する。表示するのは許容表記の第一項目と指示で、読みは表示しない。
- タッチの回数と時刻：`adb shell getevent -lt`で、試験中だけタッチの開始（`ABS_MT_TRACKING_ID`の新しい値）と時刻を記録する。キー操作数と完了時間はこの記録から数える。記録は課題文の入力中だけに限り、試験の終了時に止める。
- 操作の分類：画面録画（`adb shell screenrecord`、開発者オプションの「タップを表示」）とタッチ座標から、各タッチを文字入力、変換・確定、候補選択、削除、その他へ分ける。キーの範囲は各IMEのスクリーンショットから実測して記録する。自動で決まらないタッチは録画を見て分類し、分類した人と判断を記録する。
- 主観：各条件の終了時に、「このまま日常で使えるか」「訂正のしやすさ」「表示の揺れが気になったか」を5段階で答え、自由記述を1〜3行残す。
- 課題の間に試験欄を空にする。空にする方法は、試験画面（`Phase2cTaskActivity`）の「空にする」ボタン、または上の`am start`とし、その操作は数えない。

## 実施順と練習

本人が操作する試験は3回に分けて行う（日を分けてよい）。各回で3条件を一つずつ行い、条件の順番とリストの割り当てを次の表で入れ替える。3回を通して、各条件は各位置（1番目・2番目・3番目）と各リストに一度ずつ当たる。

| 回 | 1番目 | 2番目 | 3番目 |
|---|---|---|---|
| 1 | S・リストA | O・リストB | N・リストC |
| 2 | O・リストC | N・リストA | S・リストB |
| 3 | N・リストB | S・リストC | O・リストA |

- リスト内の課題の順番は、固定seed（仮に`20261001`）で並べ替えた順とし、seedと順番を記録する。
- 各条件の開始前に、練習の6文を行う。練習の結果は集計しない。Uzumiの条件では、練習の後に学習履歴を消してから本番を始める。
- 各回の前に、ライブON/OFFの切り替え方と過去訂正の操作を口頭ではなく手順書で確認する。手順書は3条件で同じ粒度にする。

## 除外条件

除外は次の条件に当てはまる課題だけとし、理由を課題IDごとに記録する。除外した課題は全条件の集計から外すのではなく、その条件のその課題だけを外す。

- 通知、着信、画面の自動回転など、試験と無関係な割り込みで入力が中断した。
- ユーザーが課題文を読み違えて別の文を入力した（本人の申告と録画で確認する）。
- 記録（getevent、録画、評価用計数）が欠けた。

次は除外しない。IMEのcrash、ANR、入力の欠落・二重入力、別の欄への書き込みは失敗として記録し、安全性の不具合として扱う。

一つの条件で除外が課題の20%（仮）を超えた場合は、その回を無効にして同じ組み合わせでやり直す。

## 合格基準（案、すべて仮の値）

以下の数値は仮であり、根拠となる測定はまだ無い。承認時に値を確定し、測定後に変えない。

| 対象 | 基準 |
|---|---|
| 安全性（必須） | 条件Nで、過去の正解の破壊、chosenの侵害、古い結果による上書き、crash、ANR、入力の欠落・二重入力が0件 |
| H1 | 条件Nの文あたり確定操作数の中央値が、条件Oより30%以上少ない（仮）。自動測定で条件Nの無介入正解文率が50%以上（仮） |
| H2 | 条件Nの文あたり訂正操作数と完了時間の中央値が、条件Oの1.1倍以下（仮）。訂正操作数の中央値が両条件とも0の場合は平均で比べる |
| H4 | 条件Nの文あたりキー操作数と完了時間の中央値が、条件Sの1.2倍以下（仮） |
| 最終正解 | すべての条件で、最終正解の割合を操作数と並べて示す。条件Nの最終正解率が条件Oより低い場合は、H1を満たしても合格としない |

- 比較は同じ課題の条件間の差（対応のある差）で行う。本人の試験は各条件18文×3回で1人分のため、結果は中央値と、文単位のbootstrapによる95%区間（10,000回、seed固定）で示す。検定の有意差を合格の条件にはしない。
- 分類ごとの結果も表と図で示す。全体が合格でも、特定の分類で安全性の不具合や大きな悪化があれば、その分類を次の作業の課題として記録する。
- 安全性の条件を一つでも満たさない場合は、他の結果に関わらずPhase 3へ進まない。

## 記録する環境情報

- 実施日時、回、条件の順番、課題の並べ替えseed、本書の固定版のcommit ID。
- 端末：機種、`getprop ro.build.fingerprint`、Android版とAPI、`wm size`と`wm density`、画面のリフレッシュレート、フォントサイズと表示サイズ、タッチ操作の振動設定。
- 状態：電池残量と充電の有無、省電力の設定、`dumpsys thermalservice`の温度状態、`adb shell am memory-limiter status`の結果。
- Uzumi：commit ID、APKのSHA-256、Mozcのcommitと`getDataVersion()`の値、キーボードの高さ、評価用計数の版。
- Simeji：`dumpsys package com.adamrocker.android.input.simeji`の`versionName`、フリック・トグル・キーボードの高さ・クラウド変換などの設定。
- 持ち方と、試験中に気づいた出来事の記録。

## データの保存と日常入力の扱い

- 生の記録（getevent、画面録画、評価用計数、uiautomatorの出力）は、Git追跡外の`.local-build/phase2c/<実施日>/`に置き、リポジトリへ入れない。画面録画は分類を終えたら削除するかを承認時に決める。
- リポジトリへは、課題IDごとの集計値、分類ごとの表、図、図の元データ（課題IDと数値だけ）、生成コードを`docs/`へ残す。
- 日常入力の本文は収集しない。評価用計数は評価モードの間だけ動き、既定では無効にする。getevent・録画は課題の入力中だけ行う。試験の途中で私的な入力をした場合は、その区間の記録を削除する。
- 課題文以外の本文、候補、clipboardをlogへ残さない。

## 固定と変更の規則

- 承認後は、課題文、許容表記、指標の定義、除外条件、合格基準、実施順、seedを変えない。
- 変える必要が見つかった場合は、本書を新しい版として理由とともに記録し、それ以前の結果は旧版の基準で判定したまま残す。旧版の結果を新しい基準で判定し直して合格にしない。
- 測定中に見つかった不具合を修正した場合は、修正前の結果を消さず、修正後の結果と版を分けて示す。

## 承認を求める事項

1. 3条件（Simeji、ライブOFF、ライブON）と、Simejiの設定・学習を現状のまま使うこと。
