# ニューラルで直接変換し、辞書で補う方式の設計案

**状態：案（2026-09-24）。** ユーザーはPhase 3aを、karukanと同じく「ニューラルで直接変換し、辞書で補う方式」で始めると決めた。本書はその方式を、既存の[ライブ変換の状態設計](live-conversion-design.md)とMozcの接続へどう合わせるかを定める。数値はすべて仮の値である。どのモデルを使うかは[評価条件の案](phase3a-model-selection-protocol.md)で決める。取得・ビルドの記録は[ローカル試作](neural-probe.md)にある。

## 結論

- ライブ変換コア（`dev.uzumi.ime.live`）の状態、照合、保護の規則は変えない。ニューラル変換は既存の`LiveConverter`の実装の一つとして入れ、コアから見るとMozcと同じ「部分範囲の読みをsegment列へ変える変換器」になる。
- 保護範囲とカーソルでの分割、ユーザー辞書と学習語の合成は、既存の`SegmentedLiveConverter`をそのまま使う。ニューラル版は、その部分範囲の変換（`convertRange`）だけを置き換える`NeuralRangeConverter`とする。
- 部分範囲の中では、かなの連なりだけをモデルへ渡す。数字、英字、記号はモデルへ渡さず入力のまま表示する（karukanの既定と同じ）。
- モデルの出力は、読みとの対応を確かめてから使う。かなの並びが読みと合わない出力は「読みに無い語の生成」とみなし、そのかなの連なりはMozcの結果を表示する。
- 文節の境界と候補はMozcから借りる。ニューラルの表記をMozcの文節へ切り分け、切り分けられない境界は隣の文節とつなぐ。各文節の候補は、ニューラルの表記を先頭に、Mozcの候補を続ける。
- 推論はIMEと別のプロセス（仮称`:neural`）で行う。モデルの異常や強制終了でIMEを巻き込まず、その間はMozcだけで入力を続ける。

## 処理の流れ

1. コアが読みの編集ごとに変換要求を出す（既存）。統合担当は直列のworkerで変換器を呼ぶ（既存の`ConversionWorker`）。
2. `SegmentedLiveConverter`が対象範囲を保護範囲とカーソルで区切り、学習した句があればその終わりでも区切る（既存）。
3. 各部分範囲について`NeuralRangeConverter`が次を行う。
   1. 部分範囲を、かなの連なりと、それ以外（数字、英字、記号、絵文字など）の連なりへ分ける。
   2. それ以外の連なりは、読みをそのまま表記にした一つのsegmentにする。
   3. かなの連なりは、Mozcで文節と候補を得て、同時にモデルで表記を得る。モデルへは、同じ部分範囲でその前に出した表記を左文脈として渡す。
   4. モデルの表記を読みに対応づけ、Mozcの文節へ切り分ける。対応づけに失敗したら、Mozcの結果を使う。Mozcも使えなければ読みのまま表示する。
4. `SegmentedLiveConverter`がユーザー辞書の登録語と学習語を合成する（既存の「ユーザー辞書 → 学習 → エンジン」の順）。
5. コアが結果を照合して、provisionalのsegmentだけを更新する（既存）。

骨組みとして、手順3（`NeuralRangeConverter`）とモデルのport（`NeuralKanaKanjiModel`）を`app/src/main/java/dev/uzumi/ime/conversion/NeuralConversion.kt`に置き、fakeのモデルを使ったJVMテストで確認した。JNI、llama.cpp、別プロセスへの接続は、本書の承認後に行う。

## 既存の状態設計との合わせ方

| 規則 | ニューラル版での扱い |
| --- | --- |
| provisional、stable、chosen | コアの規則のまま。ニューラルの結果もprovisionalのsegmentだけを更新する。stableへの昇格の観測回数は読みrevisionごとに数えるため、同じ入力にMozcとニューラルの二つの結果が届いても二重には数えない（既存の`lastObservedReadingVersion`） |
| 保護範囲 | `SegmentedLiveConverter`が保護範囲の境界で必ず区切り、保護範囲はモデルへ渡さない。保護範囲の表記は、後ろの部分範囲の左文脈として使う（下記） |
| カーソル境界 | 対象範囲の内部にあるカーソルで必ず区切る（既存）。カーソルより右の読みは右文脈として使わない。zenz v3.2は右文脈の記号を持つが、初期案では使わない |
| 古い結果の破棄 | 3段で行う。①workerは未処理の要求を最新の一件だけ残す（既存）。②別プロセスへの要求に番号を付け、新しい要求が来たら古い推論を中断する（スミレのabort callbackと同じ方法）。③コアがepoch、revision、読み、対象範囲、保護範囲、世代を照合する（既存）。中断できずに遅れて届いた推論結果は、①の段階で要求番号が合わず捨てる |
| 世代（`converterGeneration`） | 辞書の世代に加えて、モデルのファイル（SHA-256）とプロンプト形式の版を含める。モデルや形式が変わった後に、前の世代の結果を適用しない |
| 学習禁止欄 | 変換不可の欄（password等）ではモデルへも読みを送らない（既存の`conversionAllowed=false`）。学習禁止の欄では、学習語を参照せず、確定を学習しない（既存）。モデルは状態を持たないため推論は行うが、左文脈は現在のcompositionの中だけに限り、別プロセス側でも入力・出力を記録しない |
| Undo／Redo | コアの規則のまま。復元した範囲は次の読みの編集まで保護され、モデルの結果で上書きされない（既存の`guardedSegmentIds`） |

### 左文脈

モデルへ渡す左文脈は、対象の部分範囲より前にある表示（保護範囲の表記と、同じ要求で先に変換した表記）とする。確定済みでEditorにある文字列は、初期案では使わない。使う場合は、学習禁止欄では使わない、読み取れた範囲だけを使う、最大64文字（仮。jinenの公表値の条件）に切る、という規則を加える。

骨組みでは、`SegmentedLiveConverter`の`convertRange`が読みだけを受け取るため、左文脈は同じ部分範囲の中で先に出した表記だけである。保護範囲の表記を渡すには`convertRange`へ左文脈の引数を足す必要があり、組み込みの段階で行う。

## 辞書（Mozc）の補い方

### 数字・英字・記号の保護

部分範囲を文字の種類で分け、ひらがな、カタカナ、長音記号（`ー`）、繰り返し記号（`ゝゞヽヾ`）、結合用の濁点・半濁点だけをモデルへ渡す。それ以外の連なりは入力のまま一つのsegmentにし、モデルへもMozcへも渡さない。これで、電話番号、金額、URL、英単語の桁や綴りがモデルの推論で変わることを防ぐ。

この規則では「だい3かい」は`[だい][3][かい]`に分かれ、`だい`と`かい`は別々に変換される（左文脈で`3`は渡す）。Mozcでの現状の動作（部分範囲がASCIIだけのときだけ入力のまま）とは異なる。数字を含む読みの変換品質は評価で確かめ、悪ければ「数字を含む部分範囲はMozcで変換する」案と比べる（要確認）。

### 読みに無い語の生成の検出

モデルの出力が読みから説明できるかを、次の順に確かめる。どれかに当たれば、そのかなの連なりはMozcの結果を使う。

1. 出力が空、制御文字、`U+FFFD`、プロンプト用の記号（`U+EE00..U+EE0F`）を含む。
2. 出力がモデルの終端tokenで終わらなかった（最大token数に達した等）。別プロセス側で判定する。
3. **かなの並びが読みと合わない。** 出力を、かな1文字ずつと、それ以外（漢字、数字、記号など）の連なりに分ける。出力のかなは読みの同じ位置の文字と一致し（カタカナはひらがなとして比べる）、それ以外の連なりは読みの1文字以上に対応する、という割り当てが一つも無ければ不採用とする。モデルが読みを落とした、足した、括弧書きを加えた、といった出力の多くがここで見つかる。
4. （組み込み時に追加）漢字以外の連なり（数字、英字、括弧など）が読みから生まれた場合は、Mozcの候補に同じ表記があるときだけ使う。「じゅうじ」から「10時」を出すような変換は、Mozcが同じ候補を持つ場合だけ許す。

骨組みは1と3を実装した。3は漢字の読みそのものは確かめない（「十字」と「十時」の違いは見分けない）。漢字の連なりもMozcで確かめる厳しい案は、評価で不採用率とflickerを測ってから決める（要確認）。

### 読みと表記の対応づけ

手順3の割り当てが一つに決まれば、出力のかなの前後を「読みと表記を同じ位置で切れる点」とする。漢字などの連なりの内部は切れない。割り当てが二つ以上ある場合（例：読み「かかかか」に出力「蚊か蚊」）は、かなの連なり全体を一つのsegmentにする。

### 文節と候補

1. 同じかなの連なりをMozcで変換し、文節の読みと候補を得る。
2. Mozcの文節境界のうち、上の「切れる点」に当たるものだけで出力を切る。切れない境界の両側の文節はつなぐ。例：読み「じゅうじから」で、Mozcの文節が`[じゅう][じ][から]`、出力が「10時から」なら、`[じゅうじ→10時][から→から]`になる。
3. つながなかった文節の候補は、ニューラルの表記を先頭にMozcの候補を続ける。つないだ文節の候補は、ニューラルの表記とMozcの表記の連結の二つにする。
4. Mozcの文節の読みを連結したものが元の読みと合わない場合（Mozcが読みを正規化した場合など）は、かなの連なり全体を一つのsegmentにする。
5. Mozcを使えない場合は、かなの連なり全体を一つのsegmentとし、候補はニューラルの表記と読みにする。

候補バーは現在の設計のまま、焦点のsegmentの候補を出す。変換キー（ライブ変換中は次の候補）もMozcの候補を順にたどる。モデルに複数の候補を出させる方法（karukanのbeam、スミレの候補評価）は計算量が増えるため初期案では使わず、評価後に候補の不足が問題になった場合に加える。

### 失敗時の辞書へのfallback

| 状況 | 表示 |
| --- | --- |
| モデルが読み込めない、別プロセスが終了した、時間を超えた | かなの連なりにMozcの結果。別プロセスは間隔を空けて再起動する |
| モデルの出力が上の検出で不採用 | かなの連なりにMozcの結果 |
| モデルの結果が使えず、Mozcも使えない | そのかなの連なりは読みのまま表示する |
| モデルの結果は使えるが、Mozcが使えない | かなの連なり全体を一つのsegmentとし、候補はモデルの表記と読み |

`NeuralRangeConverter`は常に読みと一致するsegment列を返し、`null`を返さない。`SegmentedLiveConverter`とコアの約束（失敗時は`null`で現在の表示を保つ）は、別プロセスの接続の段階で「モデルもMozcも初期化前」の場合に使う。

時間超過の判定はworker側で行い、超えた要求はMozcの結果を返して終える。後から届いたモデルの結果は要求番号が合わないため捨てる。一つの要求に二度結果を返さないため、「Mozcを先に出してから、ニューラルで置き換える」二段の表示は初期案では行わない。二段にするとflickerが増えるためである。

## ユーザー辞書と学習キャッシュとの合成

- 候補の順は既存の「ユーザー辞書 → 学習 → エンジン」を保つ。ニューラル版では「エンジン」の中が「ニューラルの表記 → Mozcの候補」になる。karukanは学習キャッシュをユーザー辞書より前に置くが、Uzumiは既存の順を変えない。
- 部分範囲全体の読みに登録語か学習語があれば、その範囲を一segmentにして登録語を表示する既存の規則を保つ。ニューラルの表記は候補に残る。
- 学習した句は、ニューラルへ渡す前に部分範囲を区切る（既存）。
- 確定時の学習は既存の`learnCommitted`のままとする。IME側の学習キャッシュ（`LearningStore`）へは表示のまま確定したsegmentを記録する。Mozcへの学習は、Mozcが同じ区切りと表記を再現できたときだけ成功し、ニューラルだけが出した表記は学習されない（既存の`learnSegments`が確定せずに取り消す）。モデル自体は学習しない。
- 学習キャッシュを消す操作は、既存どおりIME側とMozcの両方を消す。モデル側に消すものは無い。

## 別プロセスでの推論と要求の中断

スミレは`android:process=":zenz"`のserviceとoneway AIDL（要求番号付きの`generate`、`cancel`、callback）で推論をIMEから分けている。Uzumiも同じ形を採る。

| 項目 | 案 |
| --- | --- |
| プロセス | 同じアプリの`:neural`。exportしないbound service |
| 通信 | oneway AIDL。`convert(requestId, reading, leftContext, maxTokens, callback)`、`cancel(requestId)`、`close()`。callbackは`onResult(requestId, text, termination)`と`onError(requestId, reason)` |
| 中断 | native側は最新の要求番号をatomicに持ち、llama.cppのabort callbackとtokenごとの確認で古い推論を止める（スミレの`abort_if_stale`と同じ）。IME側は新しい要求を送る前に古い番号を`cancel`する |
| 異常 | `binderDied`や時間超過が続いたら、モデルを使えない状態としてMozcだけで続ける。再起動は回数と間隔を制限する |
| 文字列 | native側の出力はUTF-8が壊れ得るため、UTF-16へ置換しながら変換して返す（スミレの`toJString`と同じ）。プロンプトの各欄からは`U+EE00..U+EE0F`と制御文字を取り除く（スミレの`sanitize_prompt_field`と同じ） |
| モデルの置き場所 | APKに同梱する場合は、初回に`no_backup`へ展開してSHA-256を確かめてから読み込む案と、非圧縮で同梱してファイル記述子から読む案がある。展開の時間と容量を測って決める（要確認） |
| 同時実行 | 推論は一つだけ。thread数は2〜4（仮）とし、実機で測る |
| cache | 読み、左文脈、モデルの世代を鍵にした小さなLRU cacheを持つ。打鍵のたびに対象範囲全体を要求し直すため、変わっていない部分範囲を再推論しない（karukanの`cache.rs`と同じ考え方） |

別プロセスにすると、モデルのメモリはIMEのプロセスと別に数えられ、低メモリ時にOSが`:neural`だけを終了できる。一方で、Android 17のアプリ単位のメモリ制限が二つのプロセスの合計にかかるかは確認していない（不明）。評価で`am memory-limiter status`と`ApplicationExitInfo`を記録して確かめる。

## 長い入力の扱い

対象範囲のかなの連なりが長いほど推論時間が伸びる。karukanは30文字（既定）ごとに区切る。Uzumiでは、stableへ昇格した前方のsegmentは保護範囲になり、モデルへ渡る範囲は自然に短くなる。それでも連なりが30文字（仮）を超える場合は、30文字以内で最も後ろにあるMozcの文節境界で区切り、前の部分を別の連なりとして変換する。この規則は組み込みの段階で実装し、骨組みには入れていない。

## メモリと速度の目標（仮置き）

測定前の仮の値であり、[評価条件の案](phase3a-model-selection-protocol.md)で承認を得てから固定する。端末はPixel 10 Pro（常用端末かは未確認）。

| 対象 | 仮の目標 | 区間 |
| --- | --- | --- |
| 打鍵から読みの表示 | p95 ≤ 50 ms（既存の目標） | 推論を待たない |
| 1回の推論（かなの連なり1つ） | p95 ≤ 100 ms | 別プロセスが要求を受けてから結果を返すまで |
| ニューラルの結果の適用 | p95 ≤ 300 ms（既存の目標） | 最新の入力の受理から、適用できる結果まで |
| 時間超過でMozcへ切り替える時間 | 300 ms | 同上 |
| `:neural`の常駐メモリ | PSS ≤ 150 MB（small）、≤ 80 MB（xsmall） | モデル読み込み後、連続入力中の最大 |
| IMEの起動 | 既存の目標のまま。モデルの準備を待たずMozcで入力できる | |
| モデルの準備 | ≤ 2 s | 初回のbindから最初の推論結果まで |
| 電池 | Mozcだけの場合より、同じ操作列で端末全体の消費が20%以内の増加 | |

## karukanとスミレから借りるもの

どちらからもコードは写していない。今後ソースを写す場合は、写したファイルの先頭に元の著作権表示とライセンスを残し、`third_party/`にNOTICEを置く。

| 借りるもの | 出典 | 使い方 |
| --- | --- | --- |
| jinenのプロンプト形式（`U+EE02`を常に付ける、カタカナ、NFKC） | karukan `karukan-engine/src/kanji/backend.rs`（MIT OR Apache-2.0） | モデルごとの形式を一か所に固定する |
| 日本語以外の連なりをモデルへ渡さない規則、長い入力を区切る規則、前の表記を左文脈にする規則 | karukan `docs/chunking.md`、`karukan-im/core/src/core/engine/chunk/` | 上記「数字・英字・記号の保護」「長い入力の扱い」 |
| 読み・左文脈・モデルを鍵にした変換結果のcache | karukan `karukan-im/core/src/core/engine/cache.rs` | 別プロセス側のLRU cache |
| zenz v3.xのプロンプト記号と前処理 | スミレ `zenz/src/main/cpp/zenz_bridge.cpp`（MIT） | zenzを使う場合の形式 |
| 要求番号による中断、出力の検査、UTF-16への変換、プロンプト欄の記号の除去 | 同上 | JNIの橋渡し |
| 別プロセスのserviceとoneway AIDL | スミレ `app/src/full/AndroidManifest.xml`、`IZenzRuntime.aidl` | `:neural`の構成 |

借りないもの：karukanの手動の区切り（`Ctrl+J`）はスマートフォンの操作に合わないため使わない。karukanの複数モデルの切り替え（遅いときに軽いモデルへ落とす）は、製品のモデルを一つにする方針と合わないため使わない。スミレのKotlin辞書変換は使わず、辞書はMozcを使う。

## 骨組みで確かめたこと

`app/src/test/java/dev/uzumi/ime/conversion/NeuralRangeConverterTest.kt`で、fakeのモデルとfakeの辞書を使い、次を確かめた。

- ニューラルの表記を辞書の文節へ切り分け、候補の先頭にニューラルの表記を置く。
- 数字をモデルへ渡さず入力のまま表示し、後ろのかなへ左文脈として渡す。
- かなの並びが読みと合わない出力、プロンプト用の記号を含む出力、モデルの失敗では辞書の結果を表示する。辞書も使えなければ読みのまま表示する。
- 漢字などの連なりの内部にある辞書の文節境界ではsegmentをつなぐ。割り当てが一つに決まらない出力は一つのsegmentにする。
- `SegmentedLiveConverter`へ差し込んだ結果を、コアが拒否せずに適用する（保護範囲とカーソルの境界を保つ）。

## 要確認

1. 数字・英字・記号をモデルへ渡さない規則を初期案とすること（「だい3かい」が分かれる）。
2. 読みとの対応の検査を「かなの並び」までとし、漢字以外の連なり（数字、英字、括弧）だけをMozcで確かめる初期案とすること。漢字の連なりまで確かめる厳しい案は評価の結果で決める。
3. 文節境界をMozcから借り、切れない境界はつなぐこと。
4. Mozcを先に出してニューラルで置き換える二段の表示を行わないこと。
5. 別プロセス`:neural`とoneway AIDLの構成、時間超過300 msでMozcへ切り替えること。
6. メモリと速度の仮の目標。
7. 候補の順を既存の「ユーザー辞書 → 学習 → エンジン」のままにすること（karukanとは異なる）。
